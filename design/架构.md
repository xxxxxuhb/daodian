# 到点 · 当前架构

> 本文是唯一架构文档。之前的截图/进程/整体方案 md 已合并到这里。
> 当前版本：Tauri 2 + Vue 3 + WebView 截屏服务；不再采用原生覆盖层。

---

## 1. 一句话

**主进程管 main、pet、快速记录、数据和提醒；截屏是同一个 daodian.exe 的独立进程 --shot-service，用 WebView 做选区/标注/OCR，Rust 只负责抓屏、编码、剪贴板和文件。**

---

## 2. 进程与窗口

```text
daodian.exe（主进程）
├─ main 窗口（WebView2，index.html）
├─ pet 窗口（WebView2，index.html?window=pet）
├─ quick capture（main 窗口的 Mini 模式）
├─ tray / 提醒 / 云同步 / 备份
└─ shot_sidecar 客户端
        │ named pipe
        ▼
daodian.exe --shot-service（截屏进程）
├─ 截图热键
├─ shot-<i> 窗口（每屏一个 WebView，shot.html）
├─ 抓屏线程（Rust / GDI）
├─ 标注 / OCR / 复制 / 另存 / 贴图
├─ 长截图 / GIF（抓帧/编码 Rust；控制条目前仍有原生窗口）
└─ pin-<id> 窗口（WebView）
```

说明：

- 主进程和截屏进程是同一个 binary，用 --shot-service 区分；
- 截屏进程由 shot_sidecar 拉起、配置、心跳和重启；
- 主进程不加载 shot 页面；截屏进程不加载 main/pet 业务；
- WebView2 运行时自己拉 renderer/GPU 子进程，属于运行时，不是业务进程。

---

## 3. 主进程

入口：

- src-tauri/src/lib.rs；
- src/main.ts / src/App.vue（按 window 参数切 main/pet/shot/pin）。

负责：

- main 窗口：待办、计划、备忘录、设置、提醒、周报；
- pet 窗口：桌面珠子，置顶、透明、点击穿透；
- quick capture：复用 main 窗口，切 Mini；
- tray、开机启动、单实例；
- 数据：store.json、templates.json、settings.json、notes/、attachments/；
- 提醒、备份、云同步（Gitee）；
- shot_sidecar 客户端：启动/停止/配置/心跳/重启；
- 截图设置和历史/贴图元数据（主进程是唯一 writer）。

不负责：

- 截图 WebView；
- 截图热键；
- 抓屏/标注/OCR/长截图/GIF 执行。

---

## 4. 截屏进程

入口：

- daodian.exe --shot-service --parent <pid>；
- lib.rs 的 run_shot_service；
- 独立 Tauri runtime，只注册 shot 命令和 shot 插件。

负责：

- 截图热键（daodian_shot）；
- shot-<i> 窗口：每屏一个 WebView，按需创建；
- 抓屏：capture.rs，GDI CreateDIBSection + BitBlt；
- 冻结/实时选区、标注、文字、工具条：ShotOverlay.vue；
- OCR：ocr.rs + ShotOcr.vue；
- 复制/另存/贴图：save.rs / exportShot.ts；
- 长截图：longshot.rs + stitch.rs；
- GIF：gifshot.rs；
- pin 窗口：PinWindow.vue。

配置：

- 主进程写 settings.json；
- 截屏进程只读/adopt 到内存，不回写整份设置；
- 截图文件写 shots/，临时文件写 temp；
- 进程退出/父进程退出时清理。

---

## 5. IPC

- Windows 命名管道：shot_core::PIPE_NAME；
- 长度前缀 + JSON；
- 单实例 mutex；
- 消息：hello / reload_config / capture / dismiss / ping / shutdown；
- 事件：ready / state / error；
- 心跳 5s，2s 超时；
- 崩溃 1s/2s/5s 退避，最多 3 次；
- 大图/大 GIF 只传路径，不走管道。

目标热键策略（当前主进程仍有 fallback，待 V2.0 删除）：

- 正常情况下由截屏进程注册截图热键；
- 服务不可用时主进程只做重启/托盘提示；
- 快速记录热键仍由主进程注册。

---

## 6. 截屏数据流

```text
热键
→ 截屏进程 trigger
→ 抓 active 屏（Rust）
→ 创建/复用 shot-<focus> WebView
→ 显示覆盖层
→ WebView shot_frame 取帧
→ 选区/标注/OCR/复制/另存
→ 关闭会话，清理临时帧
```

当前实现细节：

- active 屏先抓先显；
- 其他屏延后到 active ready 之后再创建/显示；
- 帧通过 shot_frame 以 BMP 返回，WebView img 解码；
- 帧用 Arc 保存，shot_frame 不在锁里 clone；
- 抓屏用 CreateDIBSection，避免 GetDIBits 二次拷贝；
- 会话有 generation，旧帧/旧事件丢弃；
- 帧 ready 后释放像素，避免双份内存。

---

## 7. 数据与存储

主进程：

- store.json：待办/计划；
- templates.json：模板；
- settings.json：所有设置；
- notes/：备忘录；
- attachments/：笔记附件；
- backups/：备份；
- .sync/：云同步状态。

截屏进程：

- shots/：截图、贴图；
- shots/live/：临时帧；
- temp：长截图/GIF 临时文件。

原则：

- 主进程是业务数据的唯一 writer；
- 截屏进程只写 shots/ 和临时目录；
- 所有写文件尽量原子写；
- 启动清理残留临时文件。

## 9. 当前性能

本机双屏实测（2880×1920 + 2560×1440，debug 构建）：

| 阶段 | 耗时 |
| --- | --- |
| 热键 → 截屏进程 | 0ms |
| active 抓屏 | 105–119ms |
| active 覆盖层出现 | 156–213ms |
| active 帧 visible | 361–420ms |
| 其中 IPC | 150–201ms |
| BMP 转码 | 3–5ms |
| WebView 解码 | 26–31ms |
| 首次绘制 | 16–23ms |
| 第二屏帧 visible | 621–733ms |

结论：覆盖层出现不慢，**帧从 Rust 到 WebView 的 IPC 是最大头**；BMP/解码/绘制都不是主要成本。

当前帧路径：

```text
capture DIB
→ Arc 像素
→ shot_frame 生成 BMP
→ IPC 14–22MB
→ Blob
→ img 解码
→ shot_ready
```

下一步优先级：

1. 降低 IPC 字节数或改共享内存；
2. 帧改 raw RGBA + ImageData / 自定义协议；
3. active 屏优先，extra 屏完全延后；
4. copy/pin/OCR 去 base64 和重复 PNG；
5. 分阶段打点保留。

## 10. 当前遗留问题

1. shot_native.rs 和 CaptureMode::Native 仍存在，但架构上已废弃。
2. 主进程仍注册 shot 命令/保留 fallback，截屏路径还没有完全收敛到服务。
3. 长截图/GIF 的控制条/预览仍是原生 Win32 窗口，计划迁 WebView。
4. 帧仍走 BMP + IPC，未做 raw RGBA/共享内存。
5. copy/pin/OCR 仍有 base64/PNG 往返。
6. 设置写盘不是所有路径都原子写。
7. 测试主要集中在 Rust；前端/截屏 E2E 不足。
8. README 的截图快捷键与当前默认值不一致。

---

## 11. 边界与决策

已经确定：

- 不再做原生覆盖层/原生选区/原生标注；
- 抓屏仍用 Rust/GDI，后续可换 WGC/DXGI；
- 截屏服务独立进程，主进程不创建 shot 窗口；
- pet 留在主进程，不拆进程；
- 主进程是设置和业务数据的唯一 writer；
- 截屏 UI 用 WebView，抓屏/编码用 Rust；
- 长截图/GIF 最终 UI 也回 WebView。

不做：

- 不维护第二套原生截图；
- 不把 pet 拆进程；
- 不引入 Qt/OpenCV/ONNX 全家桶；
- 不做云服务/微服务；
- 不在数据量还小时上 SQLite。

---

## 12. 近期收敛顺序

1. 删除 shot_native / CaptureMode::Native / 主进程 shot 窗口与预热；
2. 主进程只保留 shot_sidecar 客户端和设置；
3. 只预热 active 屏，extra 屏按需；
4. 帧路径改 raw RGBA/共享内存，优先把 IPC 从 150–200ms 降下来；
5. copy/pin/OCR 去 base64；
6. 长截图/GIF 控制条/预览迁 WebView；
7. 补截屏 E2E 和性能回归。

---

**主进程管业务和 pet，截屏服务管 WebView 截屏；抓屏/编码 Rust，界面/标注/OCR WebView。当前最大瓶颈是帧 IPC，下一步先降传输，再删 native 遗留。**
