# 云同步改造方案 · Gitee 私有库

> 原则：**本地是唯一真实来源，远端只是副本**。启动只读本地文件；远端只在「同步」时访问，且先下载到临时目录、校验、再替换。
> 不依赖 git 命令行，全部走 Gitee OpenAPI v5（纯 HTTPS）。

## 0. 一页结论

| 项 | 决定 |
| --- | --- |
| 服务方 | Gitee 私有仓库 |
| 通道 | Gitee OpenAPI v5（https://gitee.com/api/v5），不用 git 客户端 |
| 同步范围 | store.json、templates.json（以后加 notes/）；**settings、令牌、备份、日志都不同步** |
| 启动行为 | 只读本地；开了自动同步也只是后台跑，失败不阻塞、不弹窗 |
| 冲突 | 实体级合并（按 id + updatedAt）+ 墓碑防复活 |
| 令牌 | DPAPI 加密存 gitee-token.dpapi，复用现有 protect_secret |
| 配置位置 | 全部在设置抽屉的「云同步」组 |

## 1. 同步什么、不同步什么

| 文件 | 同步 | 说明 |
| --- | --- | --- |
| store.json | 是 | 待办与计划 |
| templates.json | 是 | 计划模板 |
| notes/（后续） | 是 | 备忘录索引与正文 |
| attachments/（后续） | 是 | 按 sha256 命名，天然无冲突 |
| settings.json | 否 | 可能含 webhook 地址等敏感信息 |
| *.dpapi | 否 | 令牌，绝不出本机 |
| backups/ · logs/ | 否 | 本机数据，不该上云 |

## 2. 配置项（settings.json 的 cloud 段）

~~~json
"cloud": {
  "enabled": false,
  "provider": "gitee",
  "owner": "",
  "repo": "",
  "branch": "",
  "dir": "daodian",
  "autoSync": true,
  "intervalMinutes": 10,
  "deviceId": "desktop-a1b2c3",
  "lastSyncAt": 0,
  "lastStatus": "idle"
}
~~~

- branch：留空表示「用仓库的默认分支」，创建时由接口返回的 default_branch 填充。
- lastStatus：idle / syncing / ok / conflict / error:<code>，只用于展示。
- deviceId：首次开启同步时生成，用于冲突文件命名与日志，不上传。
- **令牌不进 settings.json**：单独存 gitee-token.dpapi，前端只拿到 hasToken（和现在 DeepSeek Key 一模一样）。

## 3. 为什么用 API 而不是 git 命令

1. 不要求用户装 git，也不需要处理凭据管理器、SSH 密钥；
2. 天然满足「不直接打开远端文件」——API 返回内容字符串，落到临时文件再校验；
3. 只访问 gitee.com 一个域名，企业网络放行更容易；
4. 不需要处理仓库克隆、LFS、历史膨胀。

**用到的接口**

| 用途 | 接口 |
| --- | --- |
| 判断远端是否变化 | GET /repos/{owner}/{repo}/commits?sha={branch}&per_page=1 |
| 读文件 | GET /repos/{owner}/{repo}/contents/{path}?ref={branch} → content(base64) + sha |
| 写文件 | PUT /repos/{owner}/{repo}/contents/{path}，body 带 sha 做乐观锁 |
| 校验仓库 | GET /repos/{owner}/{repo} → 检查 private 必须为 true |

- 令牌 scope：**projects**（建库、读写文件）+ **user_info**（GET /user 拿登录名，用来判断仓库是否已存在）。只给 projects 的话 GET /user 会 401，一键建库的第一步就断。
- HTTP 客户端用 ureq（同步、轻、rustls），比 reqwest 省依赖；已有线程模型，不需要 async runtime 扩张。


## 3.5 一键创建仓库（不需要用户去网页建）

目标：用户只填一个令牌，点一次「创建并连接」，仓库就有了。

~~~text
点「创建并连接」
  GET /user                          → login（顺带验证令牌）
  GET /repos/{login}/{repo}
    200 → 已存在：private ? 直接用 : 拒绝并提示换名
    404 → POST /user/repos { name, private: true, auto_init: true, description }
           → 返回 default_branch（Gitee 通常是 master，不是 main）
  PUT contents/{dir}/store.json      → 推本地当前数据（别留空仓库）
  PUT contents/{dir}/templates.json
  保存配置：owner=login, repo, branch=default_branch
~~~

**四个关键点**

1. **auto_init 必须为 true**。建空仓库没有分支，contents API 全部 404，后面所有推送都会失败。
2. **分支不能写死**。以接口返回的 default_branch 为准；方案里配置默认值改成空字符串。
3. **仓库名要清洗**。默认 daodian-sync，只保留字母、数字、- 和 _，避免中文/空格导致 400。
4. **404 有歧义**。令牌权限不足时，私有库也会 404。若接着创建报「名字已存在」，说明是权限问题，提示用户换一个带 projects 权限的令牌。

**失败对照**

| 状态 | 含义 | 给用户的提示 |
| --- | --- | --- |
| 401 | 令牌无效或过期 | 重新填写 |
| 403 | 令牌 scope 不足 | 重新生成，勾选 projects + user_info |
| 400 / 422 | 名字非法或已存在 | 换个名字 |
| 5xx | Gitee 抖动 | 稍后重试，不阻塞使用 |

**新建命令**

~~~rust
cloud_create_repo(name: String) -> RepoInfo   // { owner, repo, branch, created: bool }
~~~

- created=true 表示这次真的建了；false 表示复用了已有仓库。
- 创建成功后立即执行一次 Push，避免「连上了但远端是空的」。

## 4. 同步算法

### 本地状态

~~~text
<数据目录>/.sync/
├─ state.json      { remoteSha, lastPullAt, lastPushAt, dirty }
├─ tombstones.json { todos: [id…], plans: [id…] }   删除墓碑
└─ tmp/            下载中的临时文件
~~~

### 启动

1. 只读本地 store.json / templates.json，全程不联网；
2. 若 cloud.enabled && autoSync，延迟 5 秒后在后台线程执行一次 Pull；
3. 无论成功失败，都不影响主窗口显示、不弹窗。

### Pull（拉取）

~~~text
GET commits?per_page=1 → remoteSha
  └─ remoteSha == state.remoteSha → 结束（不下载任何文件）
GET contents/{path} → 写入 .sync/tmp/<file>
  └─ JSON 解析失败 → 中止，保留本地，状态置 error
合并（见第 5 节）→ 原子替换本地文件 → 更新 state.remoteSha
~~~

### Push（推送）

~~~text
本地 dirty == false → 跳过
对每个文件：
  GET contents → 拿远端 sha
  PUT（带 sha）
    └─ 报 sha 不匹配 → 先 Pull + 合并 → 重试一次
成功 → 更新 state.remoteSha、lastPushAt、清 dirty
~~~

**请求预算**：一次同步最多 5 个请求（2 次 GET + 2 次 PUT + 1 次 commit 查询）。Gitee 有频率限制，**不要轮询**，最小间隔 5 分钟。

## 5. 冲突合并

按实体合并，不按文件：

| 情况 | 处理 |
| --- | --- |
| 同 id，两边都有 | 取 updatedAt 大的一方 |
| 本地删除、远端还在 | 用墓碑压掉远端（否则会复活） |
| 从历史恢复了一版 | updatedAt 置为当前时间，并立即标脏推一次 |
| 远端删除、本地还在 | 本地 updatedAt 更新则保留，否则删除 |
| 两边 updatedAt 相同但内容不同 | 写入本地 store.conflict.<deviceId>.json，状态置 conflict 并提示 |

**墓碑**是这次改造最大的新增面：现在的 Todo / Plan 没有删除记录，删掉就没了。需要在删除时写一条 {id, deletedAt} 到 tombstones.json，保留 30 天后清理。

## 6. 本地写入的改造（前置）

Library::persist 现在是 fs::write 直接覆盖：

~~~rust
// 现在
fs::write(&self.path, raw)?;

// 改成
fs::write(&tmp, raw)?;
fs::rename(&tmp, &self.path)?;
dirty.store(true, Ordering::SeqCst);   // 供同步线程消费
~~~

- 原子写解决两件事：崩溃不写坏、同步读到半截。
- dirty 加 30 秒防抖，避免每敲一个字就推一次。

## 7. 命令（Tauri）

~~~rust
cloud_status()                     -> CloudStatus     // 是否启用、lastStatus、lastSyncAt、hasToken
cloud_save_config(cfg: CloudConfig)-> CloudStatus     // 不含令牌
cloud_set_token(token: String)     -> CloudStatus     // DPAPI 加密落盘
cloud_clear_token()                -> CloudStatus
cloud_create_repo(name: String)    -> RepoInfo        // 一键建库并连上
cloud_test()                       -> CloudReport     // 校验令牌 + 仓库私有 + 可写

~~~

CloudReport：{ pulled: bool, pushed: bool, files: [...], conflict: bool, message: String }

## 9. 安全

- 令牌用 DPAPI 加密（复用 settings.rs 里现成的 protect_secret / unprotect_secret）；
- 日志里对 access_token 做脱敏（现有 logging 加一条过滤）；
- 测试连接时若发现仓库是公开的，**拒绝保存并提示**；
- 同步失败的错误信息只保留状态码和一句原因，不回显请求体。

## 10. 失败与离线

| 情况 | 行为 |
| --- | --- |
| 断网 | 跳过本轮，状态 error:offline，不打扰 |
| 令牌过期 | 状态 error:auth，标题栏图标红点，点开提示重新填 |
| 仓库被删 / 改名 | error:repo，提示检查 owner / repo |
| 连续失败 | 指数退避 1 → 2 → 5 → 15 分钟，最多 5 次，之后静默等手动 |
| 启动时失败 | 只写日志，不弹窗、不阻塞 |

## 14. 实时性：为什么不用 Gitee Webhook

Gitee 的 Webhook 是「仓库有提交 → 它向一个 URL 发 POST」。方向是服务端 → 你，所以：

- 桌面端没有公网地址，`127.0.0.1` 对 Gitee 的机房来说就是它自己；
- 要收就得有公网端点：内网穿透（Cloudflare Tunnel / frp）、中转服务器、或第三方 relay。三者都违背「不搞服务器」，还多一个常驻进程和暴露面；
- 机器休眠/关机时 webhook 直接失败，Gitee 重试几次就放弃，反而不如轮询可靠；
- 收益也有限：数据是人手动改的，秒级实时没有意义。

**结论：不做 Webhook，把轮询做得像 Webhook。**

| 场景 | 触发 | 说明 |
| --- | --- | --- |
| 后台 | 每 intervalMinutes（默认 10，最小 5） | 现有行为 |
| 前台 | 每 60 秒 | 窗口可见时才跑，休眠不耗 |
| 窗口聚焦 | 立即一次（节流 60s） | 切回来就有最新数据 |
| 手动 | 「立即同步」/ 点云图标 | 已有 |
| 保存后 | 30 秒防抖推送 | 已有 dirty 机制 |

成本：单次同步 1 个请求（查 head commit），无变化就结束；一天几百次，远低于限流。

**以后要真多端实时**：正确姿势是后台服务（CloudBase / LeanCloud）或一台常开设备，不是 webhook + 桌面。
