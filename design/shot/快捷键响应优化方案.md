# 到点 · 快捷键响应优化方案

> 状态：**优化方案**（2026-11）· 只针对「按下 Ctrl+Alt+A 到看见冻结图」这一段，不改产品交互。
> 对象：当前 `trigger → shot worker → capture_screens → show_all → WebView readFile → onImage` 链路。
> 目标：温启动活动屏 ≤ 100ms 出现，≤ 200ms 看见冻结图；冷启动首次 ≤ 250 / 350ms；不要把「所有屏抓完」作为显示前提。
> 结论先行：**快捷键本身不慢，慢在热路径上「等所有屏 + PNG 落盘再读回 + show 早于图片 + 预热排队」四件事。** 先做活动屏先出和深色兜底，再砍掉 PNG 往返，最后才考虑原生冻结层。

---

## 0. 一页结论

| 优先级 | 改动 | 预期 | 工期 | 风险 |
| --- | --- | --- | --- | --- |
| A0 | 深色兜底 + 只 show 一次 + 去掉白色/主题底色 | 不再白闪，体感立刻稳 | 0.5 天 | 低 |
| A1 | 活动屏先抓先出，其他屏并行补 | 不再等最慢屏；配合 B 到 80–150ms | 1–2 天 | 多屏一致性 |
| B | 热路径去掉 PNG，原始帧/BMP 直接给 WebView | 每屏省 100–300ms | 2–4 天 | 传输/内存 |
| C | 独立 `shot.html` + 可取消预热、Open 优先 | 冷启动少 150–500ms | 1–2 天 | 构建拆分 |
| D | `CreateDIBSection` 直写、缓冲复用 | 抓屏 20–50ms | 1–2 天 | GDI 细节 |
| E | 原生冻结层兜底 | 热键→可见 30–80ms | 1–2 周 | 重写标注/工具条 |

**建议顺序：A0 → A1 → C → B → D；E 只在 A+B+C 后冷启动仍 >300ms 时考虑。**

## 1. 现状：时间花在哪

### 1.1 链路

```text
t0 按下快捷键
  │  全局快捷键 handler：trigger()
  │    - 设 PHASE / OPENED_AT
  │    - send_command(Open)
  ▼
t1 shot worker 收到 Open
  │    - 如果 prewarm 正在跑，Open 排在后面
  ▼
t2 capture_screens
  │    每屏并行：BitBlt → GetDIBits → BGR 交换 → PNG 编码 → 写盘
  │    join 所有屏（等最慢的一屏）
  ▼
t3 show_all
  │    每屏 ensure_shown：
  │      ensure_window → set_position/size → window.show → webview.show → emit
  │    然后 reveal_shot_windows 再 show 一遍
  ▼
t4 WebView
  │    shot-refresh → readFile → Blob → 解码 → onImage
  ▼
t5 首次 paint / 可交互
```

### 1.2 按阶段拆

| 阶段 | 现在做什么 | 为什么会慢 | 代码 |
| --- | --- | --- | --- |
| t0→t1 | 全局快捷键 → `trigger` → 发 `Open` | 本身很快；但 `Open` 和 `Prewarm` 共用 `WORKER`，预热未完成时排队 | `trigger` / `ensure_worker` / `do_prewarm` |
| t1→t2 | 每屏抓屏线程，全部 join | 等最慢一屏；每屏 PNG 编码 + 写盘；4K 两遍 33MB 级搬运 | `capture_screens` / `capture_rect` / `write_png` |
| t2→t3 | 逐屏 `window.show` / `webview.show` / reveal | 一屏 show 三次；窗口创建/显示在主线程；多屏串行 | `show_all` / `ensure_shown` |
| t3→t4 | `readFile` + Blob + 解码 | 全量读 PNG 到 JS，再解码；4K 几十 MB 拷贝 | `showFrame` / `onImage` |
| 观感 | 图片未就绪时窗口已出现 | stage 透明但窗口不透明，露出主题底色；`shot_ready` 只打日志 | `shot_ready` / `.shot-stage` |

### 1.3 关键判断

- 全局快捷键 handler 本身通常只有 **10–30ms**，不是主因。
- 真正的主因是 **「等所有屏抓完」+「PNG 编解码/磁盘往返」+「show 早于图片」**。
- 冷启动首次慢，通常还叠加 **WebView 创建/预热排队**；热启动慢则更多是抓屏和图片路径。

## 2. 目标

> 下表是 **A+B 完成后的最终目标**，不是 A1 单独就能达到；A1 先用现有 PNG 时，活动屏大概 150–300ms。

| 指标 | 温启动 | 冷启动首次 | 说明 |
| --- | --- | --- | --- |
| 热键 → 活动屏可见（深色挡输入层） | ≤ 80ms | ≤ 200ms | 用户先看到「有反应」 |
| 热键 → 活动屏冻结图 | ≤ 200ms | ≤ 350ms | 1080p / 3440×1440 |
| 热键 → 活动屏冻结图（4K） | ≤ 300ms | ≤ 450ms | 单屏 |
| 热键 → 所有屏就绪 | ≤ 300ms | ≤ 500ms | 多屏 |
| 冷启动首次不排在预热后面 | 0ms | 0ms | Open 优先 |
| 白/主题色闪烁 | 0 次 | 0 次 | 深色兜底 |

## 3. 方案

### A0. 先止血：深色兜底 + 只 show 一次（0.5 天）

**问题**：当前 `.shot-stage` 透明，但 shot 窗口没有 `transparent(true)` 或深色 `background_color`；图片未到之前，露出的是窗口/主题底色（浅色主题接近白/浅灰），`正在冻结…` 就浮在上面。用户第一眼看到的是白屏，不是冻结图。

**改法**：

1. shot 窗口设置深色背景（例如 `#0C1F1A`），或 `transparent(true)` + stage 深色兜底；两者选一，先保证不露白。
2. `ensure_shown` 只 `show` 一次，去掉重复的 `webview.show` 和 `reveal_shot_windows`；如果 WebView 必须单独 show，也只在第一次做。
3. 图片未 ready 时显示深色层 + 小号「正在冻结…」，不要显示窗口底色。
4. 可选：加 `shot_ready` 计数，只用来撤 loading，不用来阻塞 show（避免隐藏 WebView 不解码时用户点到桌面）。

**预期**：白闪消失；「慢」的体感至少变成「暗一下」，而不是「白一下」。

**文件**：`src-tauri/src/shot.rs`、`src/features/shot/ShotOverlay.vue`、`src/features/pet/pet.css`。

**风险**：窗口透明在部分显卡/远程桌面下表现不同；优先用深色 `background_color` 兜底。

### A1. 活动屏先出，不等所有屏（1–2 天）

**问题**：`capture_screens` 用 `thread::scope` join 所有屏，`show_all` 才逐屏 show。活动屏也要等最慢的屏，且每屏 PNG 编码写盘。

**改法**：

1. 触发时先确定 **鼠标所在屏**（`GetCursorPos` + 各 monitor rect），记为 active。
2. 每屏一个抓屏线程；active 屏的线程抓完（先不编码 PNG，或编码完立刻）通过 channel 把结果发给 shot worker。
3. shot worker 收到 active 结果就 **立刻 show active 屏**：创建/定位（已预热则复用）→ 深色遮挡 → 绑帧 → show。
4. 其他屏继续并行抓；每完成一屏补一屏，不阻塞 active。
5. 所有屏完成后做一次最终收尾：去掉 loading、focus active、记录 t3/t4。
6. show 依然走主线程，但 active 只做一次，其他屏批量补；不要每屏三次 show。

**预期**：多屏不再「一块一块等」，活动屏先可用；不编码 PNG 的版本配合 B 才能到 80–150ms，先用现有 PNG 预计 150–300ms。

> 活动屏 overlay 只覆盖该屏，其他屏的抓屏线程抓的是各自的 monitor 矩形，不会把 active overlay 截进去。

**风险**：活动屏先显示时，其他屏还在缩略/实时画面，持续几十毫秒；如果要求所有屏严格同一瞬间，可先并行抓 raw（不编码）再统一 show，raw 抓完通常 30–80ms。

**文件**：`src-tauri/src/shot.rs`（`capture_screens` / `show_all`）、`ShotOverlay.vue`。

---

### B. 热路径去掉 PNG（2–4 天，收益最大）

**问题**：当前 `capture_screens` 每屏都 `write_png`（`Fast` + `NoFilter` + RGBA），然后前端 `readFile` 读回、Blob、解码。展示一张冻结图，做了「编码 + 写盘 + 读盘 + 解码」四次全量工作；4K 每屏原始 33MB，PNG 仍可能 5–20MB。

**改法**：

1. 抓屏线程产出**原始帧**：`Frame { index, width, height, stride, bytes, format }`；不编码 PNG、不写盘。
2. 传输优先选一种：
   - 自定义协议 `shot://frame/{index}`，返回原始 RGBA/BGRA 或 BMP；
   - `tauri::ipc::Response` / `Channel` 原始字节；
   - 共享内存 + 自定义协议读取（Rust 侧持 mapping）。
3. 前端 `fetch` / `invoke` 拿 `arrayBuffer`，用 `createImageBitmap(new ImageData(...))` 或 BMP Blob 直接显示；不再 `readFile` + Blob 双拷贝。
4. 原始帧在「该屏 onImage」后释放；会话结束兜底释放。3×4K 峰值约 100MB，比 PNG 解码峰值可控；内存吃紧就先只保留 active 屏。
5. PNG 只保留给最终保存：前端 `toBlob` → Rust 写 bytes；不要在展示路径 `write_png`。

**最小验证顺序**：BMP（无压缩、浏览器解码快）→ raw RGBA → 共享内存。先用 4K 单屏 A/B，确认不是 IPC 带宽瓶颈。

**预期**：每屏省 100–300ms；温启动热键→冻结图有机会进入 100–200ms。

**风险**：原始帧 IPC 带宽/内存；需要 feature flag，失败回退现有 PNG 路径。

**文件**：`src-tauri/src/shot.rs`、`ShotOverlay.vue`、`Cargo.toml` / capabilities。

### C. 轻量入口 + 可取消预热（1–2 天）

**问题**：`ensure_window` 现在仍然创建 `index.html?window=shot`，每个 shot 窗口加载完整 Vue 应用（约 978KB JS + 82KB CSS）；`do_prewarm` 在启动时创建每屏一个，并且和 `Open` 共用 `WORKER`，预热未完成时第一次热键要排队。

**改法**：

1. 新增 `shot.html` + `src/shot.ts`，只加载 ShotOverlay + 少量 reset CSS，不加载 `App.vue` / AppShell / Tiptap / notes / pet。
2. Vite `build.rollupOptions.input` 增加 `shot.html`；Rust 的 URL 改为 `shot.html?screen=N`。
3. 预热放独立低优先级线程/队列，不要和 `Open` 共用 worker；`trigger` 时设置取消标记，`Open` 永远优先。
4. 截图关闭时不预热；启动后延迟 1–3 秒、一屏一屏创建；每屏记录 `build → show → onImage` 时间。
5. 给 WebView2 加后台节流相关参数，实测隐藏窗口能否解码；如果预热没有改善首帧，就只保留按需创建。

**预期**：冷启动少 150–500ms；每个 shot 窗口少解析约 1MB JS/CSS；内存更低。

**风险**：样式拆分、开发/生产入口差异；先保证主窗口不受影响。

**文件**：`shot.html`、`src/shot.ts`、`vite.config.ts`、`src-tauri/src/shot.rs`。

### D. 抓屏本身（1–2 天）

**问题**：`capture_rect` 先 `CreateCompatibleBitmap`，再 `GetDIBits` 拷进 `Vec`，再 BGR→RGB 全量交换；4K 每屏两次 33MB 级搬运。

**改法**：

- `CreateDIBSection`（top-down 32bpp）+ `BitBlt` 直接写 DIB bits，省掉 `GetDIBits` 的第二次拷贝；
- BGR→RGBA 交换放到编码/传输线程，或分块并行；
- 复用每屏 DIB / 缓冲，避免每次分配零初始化 33MB；
- 多屏限制并发（如 2 个），或给抓屏线程 `THREAD_PRIORITY_BELOW_NORMAL`，先保 UI；
- 后续再评估 WGC / DXGI，不要一上来就换。

**预期**：抓屏 30–80ms → 20–50ms，峰值内存下降。

**风险**：DIB 方向、GDI 资源生命周期、DPI；逐屏像素对比。

### E. 如果还不够：原生冻结层（1–2 周）

**什么时候考虑**：A+B+C 完成后，**冷启动首次仍然 >300ms**，或 WebView 创建/首帧始终压不下来。

**做法**：

- 每屏一个 Win32 窗口，`CreateDIBSection` 直接 `BitBlt`；
- `WM_PAINT` 直接画冻结位图，选区/标注用 Direct2D 或 GDI+；
- 工具条可以是单独的**小** WebView/native 窗口，不要整屏 WebView；
- 热键→可见约 30–80ms，没有 PNG/解码。

**代价**：选区、把手、标注、工具条、贴图都要重写一遍；约 1–2 周。**先不要做**，除非 A+B+C 仍不达标。

**兜底**：`ms-screenclip:` 调 Windows 截图工具，零维护，但没有原位贴图/自定义标注；只能当临时退路。

## 4. 实施顺序

| 阶段 | 内容 | 工期 | 依赖 | 验收 |
| --- | --- | --- | --- | --- |
| A0 | 深色兜底、单次 show、去白闪 | 0.5 天 | 无 | 不再看到主题白底 |
| A1 | 活动屏先出、其他屏补 | 1–2 天 | A0 | 不再等最慢屏；配合 B 到 ≤150ms（温） |
| C | shot.html + 预热可取消 | 1–2 天 | 无 | 冷启动不再排队 |
| B | 原始帧/BMP，去 PNG | 2–4 天 | A1 | 每屏省 100–300ms |
| D | CreateDIBSection + 复用 | 1–2 天 | B 可并行 | 抓屏 ≤ 50ms |
| E | 原生冻结层 | 1–2 周 | A+B+C 仍不达标 | 热键→可见 ≤ 80ms |

**建议第一周只做 A0 + A1 + C**：先把「按了有反应」和「冷启动不排队」解决；B 是第二周的主菜。

## 5. 测量

### 5.1 现有日志

- `screenshot captured`：所有屏抓完/写完（t2）。
- `screenshot session opened`：`show_all` 完成（t3）。
- `screenshot frame ready`：每屏 `onImage`（t4）。

用这三条就能先定位：

| 现象 | 结论 | 先做 |
| --- | --- | --- |
| `captured` 很大 | 抓屏/PNG/写盘慢 | B / D |
| `captured` 到 `opened` 差距大 | show/窗口/预热慢 | A0 / A1 / C |
| `opened` 到 `frame ready` 差距大 | 读图/解码慢 | B |
| 只有冷启动第一次慢 | WebView 创建/预热排队 | C |

### 5.2 建议补的标记

- t0 快捷键 handler 收到；
- t1 shot worker 收到 `Open`；
- t2 active 屏抓完；
- t3 active 屏 show；
- t4 active 屏 onImage；
- t5 all ready。

前端再加 `performance.mark("shot-key")` / `shot-visible` / `shot-image-ready`，区分「窗口可见」和「图可见」。

### 5.3 测试矩阵

- 1 屏 1080p / 3440×1440 / 4K；
- 2–3 屏 4K；
- 100% / 125% / 150% DPI；
- 冷启动第一次 vs 预热后；
- 截图关闭 / 开启；
- 重复快速按 10 次，确认不排队、不闪。

## 6. 验收

1. 温启动：热键 → 活动屏可见 ≤ 80ms；活动屏冻结图 ≤ 200ms（1080p/3440），4K ≤ 300ms。
2. 冷启动首次：活动屏可见 ≤ 200ms；冻结图 ≤ 350ms（4K ≤ 450ms）。
3. 所有屏就绪 ≤ 300ms（温）/ 500ms（冷）。
4. 不再出现主题白底/浅色闪；第一帧是深色或冻结图。
5. 首次热键不排在预热后面；连续按 10 次不出现「按了没反应」。
6. 活动屏先出时，其他屏不出现白闪/焦点乱跳。
7. 输入在覆盖层出现后被挡住；不会误点桌面。
8. 原始帧路径失败能回退 PNG，行为一致。
9. 冷启动不因为预热造成主线程 >50ms 卡顿。
10. 多屏、负坐标、竖屏、125%/150% DPI 不错位。
11. 原有 Esc 分层、贴图、保存、复制回归通过。
12. feature flag 关闭可回到现有链路。

---

## 7. 这一轮不做什么

- 不先上 WGC / DXGI：采集升级放 D 之后，先砍 PNG 和 show 时序。
- 不做「等所有屏 ready 再 show」：用户会点到桌面；先显示深色挡输入层。
- 不做实时透明层「选完再截」：菜单/动画会跑，截图内容不可控。
- 不在热路径保留 `readFile` + Blob 双拷贝。
- 不为了快省略冻结：先保证内容一致，再压缩延迟。

---

## 8. 一句话

**热键响应的瓶颈不在快捷键，而在「等所有屏 + PNG 落盘再读回 + show 早于图 + 预热排队」。先深色兜底 + 活动屏先出，再把 PNG 从热路径拿掉；WebView 冷启动仍是瓶颈时，才上原生冻结层。**
