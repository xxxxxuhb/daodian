# 到点 · 另存优化方案

> 状态：**优化方案**（2026-11）· 只针对「Ctrl+S / 另存为」这一段，不改产品交互。
> 范围：从点下「另存」到文件落盘：是否正确、是否卡主线程、是否覆盖用户选的文件、是否有反馈、取消后能否回到原选区。
> 快捷键和冻结层分别见 [快捷键响应优化方案.md](快捷键响应优化方案.md)、[冻结优化方案.md](冻结优化方案.md)。
> 结论先行：当前另存路径做了 **`toBlob` → FileReader base64 → Rust 解码 → Rust 再编码** 四次全量工作；4K 会卡 0.5–1s。另存不需要重写，改成 **直接传字节 + 直接写盘 + 修正覆盖语义 + 保存反馈** 即可。

---

## 0. 一页结论

| 优先级 | 改动 | 预期 | 工期 | 风险 |
| --- | --- | --- | --- | --- |
| S1 | 覆盖语义修正：用户选覆盖就覆盖，不再自动 `-2` | 不再出现「选了覆盖却存成 -2」 | 0.5 天 | 低 |
| S2 | 直接传字节：去掉 FileReader base64 / Rust 重复编解码 | 4K 不再卡 0.5–1s | 1 天 | 二进制 IPC 支持 |
| S3 | 原子写 + 失败清理 | 失败不留半个文件 | 0.5 天 | 低 |
| S4 | 默认目录 / 记住上次目录 / 时间文件名 | 少点几次目录 | 0.5–1 天 | 低 |
| S5 | 保存成功提示 + 可选打开文件夹 | 知道存到哪 | 0.5 天 | 低 |
| S6 | `SAVING` 期间禁用截图热键 / Esc 冲突 | 对话框不会被二次截图打断 | 0.5 天 | 低 |

**建议顺序：S1 → S2 → S3 → S4 → S5 → S6。** S1 是正确性，先修；S2 是性能，收益最大。

## 1. 现状：另存链路

```text
前端 saveImage()
  commitText()
  renderPng(chosenBox())
    使用缓存 exportFrame（ImageBitmap）；没有就 createImageBitmap 一次
    canvas.toBlob("image/png")        // 异步编码
    blobToBase64()：FileReader 读成 base64
  invoke("shot_save", { png: base64 })

Rust shot_save()
  decode_png(base64)                // 再解码一次
  SAVING = true
  conceal_shots()                   // Suspend + 等 worker，最多 5s
  blocking_save_file()              // 系统另存对话框
  SAVING = false
  取消 → reveal_shots()
  确认 → unique_png(ensure_png(path))
       → write_png(Fast / NoFilter / RGBA)
       → release_overlay()
```

### 1.1 具体问题

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | `toBlob` 后再走 FileReader base64 | 主线程不再同步编码，但 base64 字符串和 IPC 拷贝仍很大 |
| 2 | base64 通过 `invoke` 传 Rust | 字符串膨胀 1/3，IPC 拷贝，内存峰值高 |
| 3 | Rust `decode_png` 后再 `write_png` | 同一张图解码/编码两次，CPU 翻倍 |
| 4 | `unique_png` 在对话框之后执行 | 用户选「覆盖」，实际写成 `xxx-2.png`，文件不在他选的位置 |
| 5 | 默认只有文件名，没有默认目录/上次目录 | 每次都要重新找文件夹 |
| 6 | 保存成功后覆盖层直接关闭 | 用户不知道存到哪，也不能打开文件夹 |
| 7 | `SAVING` 只挡 Esc，没挡全局截图热键 | 对话框开着时再按截图，可能起新会话 |
| 8 | `conceal_shots` 等 worker 最多 5s | worker 忙时，保存对话框迟迟不出来 |
| 9 | `write_png` 直接写目标文件 | 写一半失败会留下半个文件/毁掉已有文件 |
| 10 | 只支持 PNG，没有保存目录设置 | 需求靠用户手动绕 |
| 11 | base64 字符串 + FileReader 仍是全量拷贝 | 4K 内存峰值高，IPC 慢 |
| 12 | 取消后恢复靠 `reveal_shots` | 基本可用，但和 `SAVING` 的时序要再确认 |

---

## 2. 目标

| 指标 | 目标 |
| --- | --- |
| 4K 另存总耗时 | ≤ 800ms（不含用户选路径） |
| 主线程阻塞 | 单次 ≤ 100ms，不能出现 0.5s 级长任务 |
| 覆盖语义 | 用户选覆盖就写到该路径，不自动改名 |
| 取消 | 回到原选区，标注不丢，覆盖层不闪白 |
| 失败 | 保留原文件，删除临时文件，覆盖层恢复并提示 |
| 默认路径 | 设置里的目录 + 时间文件名；记住上次目录 |
| 反馈 | 成功后有「已保存到…」提示，可打开文件夹 |
| 冲突 | 对话框期间截图热键 / Esc 不产生二次会话 |

## 3. 方案

### S1. 覆盖语义：先修正确性（0.5 天）

**问题**：`shot_save` 在用户确认路径后调用 `unique_png(ensure_png(path))`。如果用户选了一个已存在的文件并在系统对话框里确认「覆盖」，代码会改成 `-2.png`，实际没有覆盖。

**改法**：

- 手动另存：**用户选什么路径就写什么路径**；覆盖确认交给系统对话框（它已经问过了）。
- `unique_png` 只用于「自动保存 / 复制后自动保存」这种没有对话框的路径。
- `ensure_png` 只在用户没写扩展名时补 `.png`；不要悄悄改目录/文件名。
- 如果目标存在且系统对话框没有覆盖确认（自定义对话框才需要），再单独提示；当前系统对话框不用。

**验收**：选一个已存在文件 → 确认覆盖 → 文件内容更新，不出现 `-2.png`。

### S2. 直接传字节：去掉 FileReader base64（1 天）

**问题**：前端 `canvas.toBlob` 已经异步，但随后用 FileReader 读成 base64；Rust 再 `decode_png` + `write_png`。4K 仍有 base64 字符串、IPC 拷贝和双重编解码。

**改法**：

1. `canvas.toBlob("image/png")` 已经异步，保留；下一步是把 `blobToBase64()` 换成直接传 `ArrayBuffer` / `Uint8Array`。
2. 继续用已有的 `exportFrame`（ImageBitmap）缓存；只有缓存没有时才 `createImageBitmap` 一次，不要重新解码原图。
3. 传输：
   - 优先：`tauri::ipc` 原始字节 / `Channel` / 自定义协议，Rust 直接拿 `Vec<u8>`；
   - 兜底：用 `plugin-fs` 把 bytes 写到临时 `.png`，把路径交给 Rust；至少去掉 base64。
4. Rust 新命令 `shot_save_bytes`：直接写 bytes，不再 `decode_png` + 重新编码。
5. 如果最终要 JPG（P2），在 `toBlob("image/jpeg", 0.92)` 时决定格式，Rust 只负责写。

**预期**：4K 另存从 0.5–1s 降到 200–500ms；主线程不再承担 base64 和同步编码。

### S3. 原子写 + 失败清理（0.5 天）

**问题**：`write_png` 直接写目标文件；磁盘满/权限/网络中断会留下半个文件，甚至破坏已有文件。

**改法**：

- 写到同目录的 `xxx.png.tmp`（或随机后缀）；
- 写完 `flush` 后 `rename` 到目标；Windows 上用 `ReplaceFile` 或先删再改名（注意保留旧文件）；
- 失败删 tmp，目标文件保持原样；
- 返回错误给前端，覆盖层恢复并提示。

**验收**：目标只读/磁盘满时，原文件不被破坏，临时文件不残留。

### S4. 默认目录、文件名、记住上次目录（0.5–1 天）

**问题**：`set_file_name` 只有时间文件名，没有默认目录/上次目录；每次都要重新找。

**改法**：

- 设置里增加「保存到」：默认 `图片\到点截图\`；不存在时创建；不可写退回数据目录下 `shots`。
- 另存对话框默认打开该目录；用户改过目录后记住「上次目录」（存设置）。
- 文件名保持 `到点截图-YYYYMMDD-HHmmss.png`；重名时：
  - 手动另存：系统对话框负责覆盖确认，不自动改名；
  - 自动保存：用 `unique_png` 加 `-2`。
- 记住上次目录只记路径，不记文件内容。

**验收**：连续另存两次，第二次默认打开上次目录；文件名不重复。

### S5. 反馈：已保存提示 + 可选打开文件夹（0.5 天）

**问题**：保存成功后覆盖层直接关闭，用户不知道文件在哪。

**改法**：

- 保存成功后，覆盖层保留 700ms，显示「已保存到 图片\到点截图\到点截图-….png」；
- 提供一个「打开文件夹」按钮（可选，调用系统 explorer）；
- 超时或点击后关闭覆盖层；
- 保存失败：覆盖层保留，显示错误 + 重试；
- 取消：不提示，恢复原选区。

**验收**：保存后能看到完整路径；打开文件夹能定位到文件；失败不关闭覆盖层。

### S6. 对话框期间的热键 / Esc 冲突（0.5 天）

**问题**：`SAVING` 只在 `handle_escape` / `hook_shortcut` 里挡；`trigger` 没有检查。对话框开着时按截图热键，可能起新会话。

**改法**：

- `trigger` 开头检查 `SAVING`，为 true 直接返回；
- 全局快捷键 handler / 托盘入口同样检查；
- `SAVING` 用 RAII guard，确保对话框异常也能复位；
- 对话框期间 Esc 交给系统对话框，不要关截图会话；
- 保存取消后 `reveal_shots`，恢复原选区。

**验收**：对话框开着时按截图快捷键无反应；Esc 只关对话框；取消后原选区和标注还在。

### S7. 性能细节

- `conceal_shots` 目前发 `Suspend` 并等 worker，最多 5s；保存对话框不必等抓屏 worker。可以先 `conceal_shot_windows()` 立即隐藏，再异步 `Close/Suspend`，避免 worker 忙时对话框迟到。
- 保存对话框不要在抓屏线程/主线程上阻塞；用命令线程/异步命令。
- `SAVING` 期间禁止新截图和贴图操作，避免状态交叉。
- 4K 内存：`toBlob` + bytes + Rust buffer 峰值要测；不要同时保留 base64、PNG bytes、RGBA。
- 保存成功后释放 `ImageBitmap` / Blob URL / canvas；取消后保留选区，不保留临时导出。

## 4. 验收

1. 4K 选区另存总耗时 ≤ 800ms（不含用户选路径）；主线程无 0.5s 级长任务。
2. 保存后粘贴/打开文件，尺寸、颜色、标注与预览一致。
3. 用户选已存在文件并确认覆盖 → 原路径内容更新，不出现 `-2.png`。
4. 手动另存不自动改名；自动保存重名才加 `-2`。
5. 默认目录正确；第二次另存默认上次目录；目录不可写有明确提示。
6. 取消保存 → 覆盖层恢复，原选区/标注不丢，不闪白。
7. 保存失败（只读/磁盘满/网络路径）→ 原文件不破坏，临时文件不残留，覆盖层恢复并提示。
8. 保存成功 → 700ms「已保存到…」提示；打开文件夹能定位。
9. 对话框期间按截图热键无反应；Esc 只关对话框；不会起第二个会话。
10. 连续保存 5 次不泄漏内存/临时文件；退出后无残留。
11. 多屏、125%/150% DPI、负坐标下保存内容正确。
12. feature flag 关闭可回到现有 base64 路径。

---

## 5. 这一轮不做什么

- 不做云盘/分享链接/截图历史。
- 不做 PDF/WebP/批量导出；JPG 只作为 P2 可选项。
- 不把「另存」做成一个完整文件管理器；只做保存路径、覆盖、反馈。
- 不在保存路径里重新解码/重编码整张图；字节从 canvas 直接到磁盘。
- 不为了省事继续用 base64；大图必须走二进制或临时文件。

---

## 6. 一句话

**另存要解决的不是「能不能写文件」，而是「别把 4K 图来回 base64、别让 Rust 重复编解码、别把用户选的覆盖偷偷改成 -2、别写坏已有文件」；直接传字节 + 直接写盘 + 原子替换 + 明确反馈，四件事做完就够了。**
