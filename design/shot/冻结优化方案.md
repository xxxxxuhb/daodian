# 到点 · 冻结优化方案

> 状态：**优化方案**（2026-11）· 只针对「冻结画面这一层」，不改产品交互。
> 范围：按下快捷键后，屏幕是否真的冻住、冻结图是否 1:1 正确、首帧是否闪白/闪暗、多屏和 DPI 是否对齐、内存和临时文件是否收得住。
> 快捷键到响应的时序另见 [快捷键响应优化方案.md](快捷键响应优化方案.md)；本文只解决「冻结层本身」。
> 结论先行：冻结本身不是坏方案；当前的问题是 **窗口先出现、图后加载、窗口又露底色**。先保证「深色挡输入层 → 活动屏先出 → 原始帧直接显示」，再决定要不要上原生冻结层。

---

## 0. 一页结论

| 优先级 | 改动 | 预期 | 工期 | 风险 |
| --- | --- | --- | --- | --- |
| F0 | 深色兜底、每个窗口只 show 一次、去白闪 | 第一眼不再看到主题白底 | 0.5 天 | 低 |
| F1 | 活动屏先抓先出，其他屏补 | 不再等最慢屏；配合 F2 到 150–250ms | 1–2 天 | 多屏一致性 |
| F2 | 原始帧/BMP 替代 PNG 落盘/读回 | 每屏省 100–300ms | 2–4 天 | 传输/内存 |
| F3 | 多屏/DPI 对齐和焦点 | 不错位、不同步、不抢焦点 | 1 天 | 低 |
| F4 | 帧生命周期和清理 | 3×4K 峰值 ≤150MB，退出即清 | 0.5–1 天 | 低 |
| F5 | 原生冻结层兜底 | 可见 30–80ms，无解码 | 1–2 周 | 重写标注/工具条 |

**建议：F0 → F1 → F3 → F2 → F4；F5 只在 F0–F4 后仍不达标时考虑。**

## 1. 现状：冻结层哪里不对

### 1.1 当前链路

```text
抓所有屏 → 每屏 PNG 编码 + 写盘 → show 所有窗口 → 前端 readFile → 解码 → 显示
```

关键问题不是「冻结」这个动作，而是**冻结图没有在窗口出现之前准备好**。

### 1.2 具体问题

| 现象 | 原因 | 位置 |
| --- | --- | --- |
| 先看到白/浅灰一大块，再看到冻结图 | stage 透明，但 shot 窗口没有深色/透明背景；图片未到，露出窗口底色 | `.shot-stage` / `ensure_window` |
| 窗口出现了但图还没到 | `show_all` / `ensure_shown` 在 `onImage` 之前就 show | `show_all` / `ensure_shown` |
| 多屏一块一块出现 | 每屏 show 独立；等所有抓完才统一 show | `capture_screens` / `show_all` |
| 冻结图边缘发虚/错位 | 物理像素、CSS 尺寸、DPI 映射不严格 | `paint` / `pixelScale` / `snapBox` |
| 画面和桌面差几帧 | 抓屏有先后；多屏不是同一瞬间 | `capture_screens` |
| 内存峰值高 | 每屏 RGBA + PNG 缓冲 + WebView 解码位图 | `capture_rect` / `write_png` / `showFrame` |
| 退出后仍有临时图 | 只用会话目录清理，异常/崩溃可能残留 | `hide_overlay` / `cleanup_leftovers` |

### 1.3 已经做对的部分

- 选区 canvas 已经改成选区尺寸，不再整屏 `fillRect`；
- 已经用 `requestAnimationFrame` 合并绘制；
- 已经缓存 stage 尺寸，不在每次 pointermove 读布局；
- 已经用 `shot-shade` 的 `box-shadow` 压暗外部；
- 已经用 `shot_ready` 记录图片就绪时间（但只打日志，没有参与显示时序）。

这些先保留，下面只补冻结层缺的部分。

## 2. 目标

| 指标 | 目标 |
| --- | --- |
| 首帧观感 | 不出现白/浅色闪；第一帧是深色层或冻结图 |
| 活动屏冻结图 | 1080p / 3440×1440 ≤ 250ms；4K ≤ 350ms（配合 F2） |
| 所有屏冻结图 | ≤ 400ms；错峰 ≤ 50ms |
| 1:1 正确性 | 100% / 125% / 150% / 200% 下选区与导出像素一致 |
| 多屏 | 负坐标、竖屏、混合 DPI 不裂、不偏 |
| 内存 | 3×4K 会话峰值增量 ≤ 150MB，结束回基线 |
| 生命周期 | 退出/崩溃后无 `shots/live` 残留 |
| 输入 | 冻结层出现后挡住桌面点击；不会误点 |

## 3. 方案

### F0. 先止血：深色兜底 + 只 show 一次（0.5 天）

**问题**：现在 `.shot-stage` 透明，但 shot 窗口没有 `transparent(true)` 或深色 `background_color`；图没到之前，用户看到的是窗口/主题底色，`正在冻结…` 浮在上面。

**改法**：

1. shot 窗口设置深色背景（例如 `#0C1F1A`），或 `transparent(true)` + stage 深色兜底；优先深色背景，兼容性最好。
2. 每个窗口只 `show` 一次：去掉重复的 `webview.show`、`reveal_shot_windows`；如果 WebView 必须单独 show，只在第一次做。
3. 图片未 ready 时显示深色层 + 小号「正在冻结…」，不要显示窗口底色。
4. 保留 `shot_ready` 计数，但只用来撤 loading，不用来阻塞 show；否则隐藏 WebView 不解码时用户会点到桌面。

**预期**：白闪消失；第一眼是深色/冻结图，不是白屏。

### F1. 活动屏先出，其他屏补（1–2 天）

**问题**：`capture_screens` 等所有屏抓完，`show_all` 才逐屏 show；活动屏也要等最慢屏。

**改法**：

1. 触发时用 `GetCursorPos` + monitor rect 确定 active 屏。
2. active 屏抓完（原始帧或最快路径）立刻 show；其他屏并行抓，完成一屏补一屏。
3. active 先显示深色挡输入层，再贴冻结图；其他屏可以晚 50–150ms。
4. 如果要求所有屏严格同一瞬间：先并行抓 raw（不编码 PNG），通常 30–80ms，再统一 show；不要让 PNG 编码决定 show 时间。
5. active overlay 只覆盖该屏，其他屏的抓屏线程抓各自 monitor，不会把 active overlay 截进去。

**预期**：活动屏先可用；配合 F2 到 150–250ms。

### F2. 原始帧替代 PNG（2–4 天，收益最大）

**问题**：展示路径做「PNG 编码 + 写盘 + readFile + 解码」四次全量工作；4K 每屏原始 33MB，PNG 仍可能 5–20MB。

**改法**：

1. 抓屏线程产出 `Frame { index, width, height, stride, bytes, format }`；展示不走 PNG、不写盘。
2. 传输选一种：
   - 自定义协议 `shot://frame/{index}` 返回 raw RGBA/BGRA 或 BMP；
   - `tauri::ipc::Response` / `Channel` 原始字节；
   - 共享内存 + 自定义协议。
3. 前端 `createImageBitmap(new ImageData(...))` 或 BMP Blob 直接显示；不要 `readFile` + Blob 双拷贝。
4. 帧在「该屏 onImage」后释放；会话结束兜底释放；3×4K 峰值约 100MB，内存吃紧就先保留 active 屏。
5. PNG 只用于最终另存；另存路径见 [另存优化方案.md](另存优化方案.md)。

**预期**：每屏省 100–300ms；首帧和拖选都更稳。

### F3. 多屏与 DPI 对齐（1 天）

- 每屏窗口位置/尺寸用物理像素；窗口 CSS 尺寸 = 物理尺寸 / scale。
- 冻结图 `naturalWidth / clientWidth` 必须等于物理/ CSS；选区吸附物理像素。
- 测试：100/125/150/200%、混合 DPI、副屏在左（负坐标）、竖屏、任务栏不在底部。
- 多屏只允许一个 active 屏响应键盘；焦点跟指针。
- 跨屏选区仍放 P2，不在这次冻结优化里做。

### F4. 生命周期与内存（0.5–1 天）

- 原始帧/Blob URL/ImageBitmap 在 onImage 或会话结束后释放；`releaseExportFrame` 已有，补齐原始帧。
- 会话结束、取消、崩溃后清理 `shots/live`；如果不再写 PNG，清理逻辑简化。
- 贴图/剪贴板临时文件单独清理，不在冻结层里。
- 不重复 destroy 窗口；复用预热的 shot 窗口，避免重建。

### F5. 原生冻结层兜底（1–2 周）

**什么时候做**：F0–F4 完成后，冷启动首次仍然 >300ms，或 WebView 首帧始终无法稳定。

**做法**：

- 每屏一个 Win32 窗口，`CreateDIBSection` 直接 `BitBlt`；
- `WM_PAINT` 画冻结位图；选区/标注用 Direct2D / GDI+；
- 工具条可以是单独的小 WebView/native 窗口，不要整屏 WebView；
- 热键→可见约 30–80ms，无 PNG/解码。

**代价**：选区、把手、标注、工具条、贴图全部重写，约 1–2 周。**先不要做**，只在 WebView 路径确实压不下来时考虑。

---

## 4. 验收

1. 首帧不出现白/主题底色；第一帧是深色层或冻结图。
2. 1080p/3440×1440 活动屏冻结图 ≤ 250ms；4K ≤ 350ms（配合 F2）。
3. 所有屏冻结图 ≤ 400ms；多屏错峰 ≤ 50ms。
4. 100% / 125% / 150% / 200% 及混合 DPI：冻结图 1:1，选区不偏、不虚。
5. 负坐标、竖屏、任务栏在侧边时，窗口覆盖正确。
6. 3×4K 峰值内存增量 ≤ 150MB；结束回基线。
7. 退出/取消/崩溃后 `shots/live` 无残留。
8. 冻结层出现后点击不会落到桌面；Esc 分层正常。
9. 贴图、复制、另存、标注回归通过。
10. feature flag 关闭可回到现有 PNG 冻结路径。

---

## 5. 这一轮不做什么

- 不做跨屏冻结/跨屏选区（P2）。
- 不做「实时透明层选完再截」：菜单/动画会跑，冻结内容不可控。
- 不先上 WGC/DXGI：先砍 PNG 和 show 时序。
- 不为追求首帧省略 1:1 正确性；冻结图必须和导出像素一致。
- 不把另存/复制路径混进冻结优化；另存单独成文。

---

## 6. 一句话

**冻结层要解决的不是「抓不抓得到」，而是「先给用户一个深色、挡输入、不闪的层，再尽快把 1:1 冻结图放上去」；PNG 落盘往返和窗口白底是当前最大的两个破坏者。**
