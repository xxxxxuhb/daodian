# 到点 · 截屏时序与覆盖层方案

> 状态：**架构方案**（2026-11）· 回答「必须先把屏截完才能操作吗？」。
> 结论先行：**不必等截屏完成才显示操作层；但要保留「触发即冻结」，就必须在触发时开始抓屏。** 当前慢是因为「截全屏 + PNG + 解码」全部排在「显示覆盖层」前面，而不是因为「截屏」这个动作本身。
> 相关：[快捷键响应优化方案.md](快捷键响应优化方案.md)、[冻结优化方案.md](冻结优化方案.md)、[优化方案.md](优化方案.md)。

---

## 0. 一页结论

| 方案 | 是否先截屏 | 首帧响应 | 内容是否冻结 | 复杂度 | 建议 |
| --- | --- | --- | --- | --- | --- |
| A. 先截全屏 + PNG + 解码，再显示（当前） | 是，全部屏 | 300–800ms | 是 | 低 | **不再走** |
| B. 只截活动屏 raw，立刻显示，其他屏补 | 是，仅活动屏 | 80–150ms | 活动屏冻结 | 中 | **先做** |
| C. 先显示透明层，选完再截 | 否 | < 50ms | 否，内容可能变 | 中 | 可选模式 |
| D. 原生覆盖层 + 并行 raw / 排除截屏 | 可并行 | 30–50ms | 可冻结 | 高，1–2 周 | 最终兜底 |

**推荐路线：B → 轻量入口/预热 → 必要时 D；C 作为可选的「实时选择」模式，不做默认。**

---

## 1. 为什么现在像「必须先截屏」

当前顺序：

```text
热键
  → 等所有屏抓完（BitBlt + GetDIBits + BGR）
  → 每屏 PNG 编码 + 写盘
  → 才 show 覆盖层
  → WebView readFile + 解码
  → 用户看到冻结图
```

用户感知到的不是「截屏」本身，而是：

- **等最慢一屏**；
- **PNG 编码/写盘/读回/解码**；
- **WebView 创建/首帧**；
- 图没到时窗口已经出现，露出底色。

所以问题不是「要不要截屏」，而是「**截屏和显示操作层被串行了**」。

最终要生成图片，当然要截屏；但**不必等截完才让用户开始操作**。可以：

1. 只截活动屏 raw，先显示活动屏；
2. 其他屏并行补；
3. 或者先显示实时透明层，选完只截选区。

---

## 2. 关键约束

### 2.1 覆盖层会被截进去

如果先显示覆盖层再截屏，截图会包含：

- 半透明暗层；
- 选区边框/十字线；
- 「正在冻结…」提示。

所以要在「先显示」和「先截屏」之间选一条：

- **先截后显**：覆盖层不会进图；代价是等待截屏（B）。
- **先显后截**：响应快；必须在截屏前隐藏覆盖层，或用 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 把覆盖层排除出截屏（C/D）。`WDA_EXCLUDEFROMCAPTURE` 需要 Windows 10 2004+，且要实测 GDI/DWM 截屏是否真的露出底层内容；如果排除后是黑块，就退回「隐藏一帧再截」。
- **先显 + 截屏排除**：响应和冻结都可兼得，但复杂，放 D。

### 2.2 实时层会让内容变化

C 方案中，用户在实时桌面上拖选：

- 视频/动画会继续动；
- 菜单、tooltip 可能因为窗口激活而关闭；
- 鼠标松开后截到的内容，可能和按下快捷键时不同。

如果用户主要截静态页面、代码、聊天记录，C 可以接受；如果经常截菜单、报错弹窗、视频帧，B 更稳。

### 2.3 WebView 创建是另一个瓶颈

即使只截活动屏 raw，如果 shot WebView 是冷的，`window.show()` 仍可能 150–500ms。B 必须配合：

- 轻量 `shot.html`（只加载 ShotOverlay）；
- 可取消预热，`Open` 优先；
- 或原生覆盖层（D）。

否则 B 只能解决「截屏等待」，解决不了「窗口创建等待」。

## 3. 方案 B：活动屏 raw 先抓，立刻显示（推荐）

### 3.1 时序

```text
t0 热键
  → 确定鼠标所在屏 active
  → 只抓 active 屏 raw（BitBlt，20–50ms）
  → 立刻 show active 覆盖层（深色挡输入）
  → 绑定 active 冻结帧
  → 其他屏并行抓 raw，抓完补上
  → 用户开始拖选
```

### 3.2 要点

1. **active 先抓**：只抓鼠标所在屏，不 join 所有屏。
2. **raw 不进 PNG**：抓完直接交给 WebView；PNG 只用于最终另存。
3. **先显示 active**：active 窗口 show 后，其他屏继续抓；不要等所有屏。
4. **深色挡输入**：active 窗口先显示深色层，图到了再贴；不要露白/主题底色。
5. **其他屏补**：其他屏抓完再 show；错峰 50–150ms 可接受。
6. **选区跨屏**：如果用户把选区拖到另一块屏，而那块屏还没 ready，显示「正在冻结」并等它；或先把该屏抓完。
7. **不截覆盖层**：B 是先抓 active 再 show，active 截图干净；其他屏在各自抓完前不显示覆盖层，也不会被截进去。

### 3.3 响应预算

| 段 | 预算 |
| --- | --- |
| 热键 → active raw 抓完 | 20–50ms |
| active raw 抓完 → active 窗口显示 | 20–80ms（轻量入口/预热） |
| active 显示 → 冻结图可交互 | 30–100ms |
| 其他屏补完 | +50–150ms |

**目标：热键 → active 可见 80–150ms；不是 300–800ms。**

### 3.4 B 的限制

- 仍然要「先截 active 再显示」，所以不是严格的「按下即可见」；但 active 只抓一块屏，代价小。
- WebView 冷启动时会退化；必须配合轻量入口/预热。
- 其他屏延迟出现；如果用户第一时间看的是副屏，仍会觉得慢。可以在热键时把**鼠标所在屏**作为 active；用户通常先看那里。

## 4. 方案 C：先显示实时层，选完再截（可选）

### 4.1 时序

```text
t0 热键
  → 立刻显示透明/浅色覆盖层（挡输入 + 十字）
  → 用户在实时桌面上拖选
  → 鼠标松开
  → 隐藏覆盖层，或把覆盖层排除出截屏
  → 只截选中区域 raw
  → 显示冻结结果 + 标注工具
```

### 4.2 优点

- 首帧 < 50ms，用户马上能操作；
- 不预先截全屏，不需要全屏图解码；
- 内存和 CPU 峰值低；
- 只截选区，尺寸小。

### 4.3 代价

- 内容不冻结：视频、动画、菜单、tooltip 会变；
- 覆盖层激活可能让菜单失焦关闭；要用 no-activate 窗口；
- 截选区前必须隐藏/排除覆盖层，否则截进暗层/边框；隐藏一帧可能闪，`WDA_EXCLUDEFROMCAPTURE` 需要实测；
- 用户拖选时看到的画面和最终截图可能差几帧；
- 如果用户拖选很快，可能松手时目标窗口还没稳定。

### 4.4 实现要点

1. 覆盖层窗口用 `WS_EX_NOACTIVATE`，不要抢焦点；否则菜单/弹窗会关。
2. 只画十字/浅暗，不要全屏深色；用户要能看见实时内容。
3. 鼠标松开后：
   - 方案 1：把覆盖层 `setIgnoreCursorEvents(true)` + 透明度 0 / 隐藏一帧，截选区 raw，再恢复；
   - 方案 2：给覆盖层设置 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`，截屏时排除它；需实测 BitBlt/DWM 是否露出底层。
4. 只截选区，不截全屏；截完显示冻结结果，再进入标注。
5. 如果用户拖选过程中窗口变化太大，可在结果预览里提供「重新选」。

### 4.5 适用

- 截静态页面、代码、聊天、表格；
- 用户明确选择「实时选择」模式；
- 不作为默认，避免菜单/动态内容截不到。

---

## 5. 方案 D：原生覆盖层（最终兜底）

### 5.1 什么时候做

- B + 轻量入口/预热后，冷启动首次仍 >300ms；
- 或 C 需要真正 <50ms 且 WebView 创建始终是瓶颈。

### 5.2 做法

- 每屏一个 Win32 透明/深色窗口，`CreateDIBSection` + `BitBlt`；
- 覆盖层直接显示，不经过 WebView；
- 截屏可在显示前/并行做；如果显示后截，用 `WDA_EXCLUDEFROMCAPTURE` 或隐藏一帧；
- 选区/标注用 Direct2D/GDI+；工具条单独小窗口；
- 热键 → 可见 30–50ms，无 PNG/解码。

### 5.3 代价

- 选区、把手、标注、工具条、贴图都要重写；
- 约 1–2 周；
- 跨屏/DPI 仍需逐台验证。

**不要把 D 当第一版**；B 是低风险、能快速验证「截屏不是必须等」的方案。

---

## 6. 推荐路线

| 阶段 | 做什么 | 目标 |
| --- | --- | --- |
| 1 | B：active 屏 raw 先抓 → 立刻显示 → 其他屏补 | 热键→active 80–150ms |
| 2 | 轻量 `shot.html` + 预热可取消 + `Open` 优先 | 冷启动不再排队 |
| 3 | 可选 C：实时选择模式 | 首帧 <50ms，接受内容变化 |
| 4 | 必要时 D：原生覆盖层 | 30–50ms，无 WebView 冷启动 |

**先做 1 + 2**。如果用户反馈「还是慢」，再决定是加 C（放弃冻结）还是上 D（重写覆盖层）。

---

## 7. 验收

1. 热键 → active 屏可见 ≤ 150ms（温启动）；冷启动 ≤ 250ms。
2. 热键 → active 冻结图 ≤ 250ms（1080p/3440），4K ≤ 350ms。
3. active 图里没有覆盖层/暗层/十字线。
4. 其他屏错峰 ≤ 150ms；所有屏 ≤ 400ms。
5. active 先显示时，用户已经可以拖选；不会因为其他屏没抓完而卡住。
6. WebView 冷启动不再排在 `Open` 后面；首次按不出现「按了没反应」。
7. C 模式下：菜单/弹窗不失焦；覆盖层不出现在截图里；内容变化在可接受范围。
8. D 模式下：原生覆盖层出现 ≤ 50ms；无白闪；DPI 正确。
9. 多屏、负坐标、竖屏、125%/150% DPI 不错位。
10. 原有标注、另存、贴图、Esc 分层回归通过。

---

## 8. 这一轮不做什么

- 不继续优化「全屏 PNG → 解码 → show」这条 A 路径；它是问题本身。
- 不把 C 做成默认；实时选择是产品取舍，不是免费加速。
- 不先上原生覆盖层；先用 B 验证「截屏不是必须等」。
- 不为了首帧省略 1:1 正确性；冻结图仍要物理像素对齐。
- 不做跨屏选区；B/C 都先单屏，P2 再跨屏。

---

## 9. 一句话

**不必等截屏完成才能操作：B 只截活动屏 raw、先显示活动屏；C 先显示实时层、选完再截；D 原生覆盖层。当前最该做的是 B + 轻量入口，先把「按了有反应」做到 100ms 级；C 是产品取舍，D 是最终兜底。**
