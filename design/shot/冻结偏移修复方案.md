# 到点 · 冻结偏移修复方案

> 状态：修复方案（2026-11）· 只处理 freeze 模式冻结图偏移/缩在一边。
> 范围：raw BMP 帧 + shot WebView 的窗口、表面和 DPI 对齐。
> 结论先行：抓屏区域本身大概率是对的（capture_bgra 用 monitor DC 的 0,0 抓）；更可疑的是冻结图已经加载，但 shot 窗口/WebView 表面还在异步改尺寸/缩放。place_shot_physical 把 finish_shot_place 又投递到主线程队列，ensure_shown 紧接着就 emit 图片刷新，图片解码和 surface 调整存在竞态。

---

## 0. 一页结论

| 优先级 | 修复 | 预期 |
| --- | --- | --- |
| P0 | surface/窗口尺寸必须在 emit 图片之前同步完成，不能再异步排队 | 消除图先到、surface 后改的偏移 |
| P1 | 统一物理像素坐标：monitor / window / client / WebView bounds / image 尺寸一致 | 固定像素偏移消失 |
| P2 | 去掉重复的 apply_shot_rect / SetRasterizationScale 调用，只在一处设置 | 避免 DPI 二次缩放 |
| P3 | 主线程补 per-monitor v2；窗口位置用物理坐标 | 混合 DPI 下窗口不偏 |
| P4 | BMP 头/行序/stride 加单测；必要时用 PNG 对照 | 排除帧数据问题 |
| P5 | 仍不稳定则退回标准 Tauri 窗口尺寸或原生覆盖层 | 兜底 |

---

## 1. 当前链路

```text
热键
  → capture_one(focus, raw)
      capture_bgra(monitor x,y,w,h)
      → LiveFrame（top-down BGRA）
      → bmp_file（bottom-up BMP）
  → show_screen
      ensure_window
      → place_shot_physical
          apply_shot_rect（Win32 SetWindowPos）
          run_on_main_thread(finish_shot_place)   ← 异步排队
      → present_shot
      → place_shot_physical 再调一次
      → emit("shot-refresh")                    ← 图先开始加载
  → WebView showFrame
      invoke shot_frame → BMP blob → img
  → finish_shot_place 可能在图之后才跑
      SetRasterizationScale / BoundsMode / SetBounds
```

关键时序问题：place_shot_physical 里把 finish_shot_place 投递到主线程，但 ensure_shown 不等待它完成就 emit 刷新；前端可能先解码图片，随后 surface 才改变尺寸/缩放。

---

## 2. 最可能的原因（按概率排序）

### 2.1 surface 设置晚于图片加载（最可疑）

- place_shot_physical 的 finish_shot_place 是 run_on_main_thread 排队的；
- ensure_shown 紧接着 emit("shot-refresh")；
- 前端 showFrame 读取 BMP、创建 blob、解码；
- 两者谁先完成不确定；
- 如果图片先画到旧 surface，surface 再改成新尺寸/缩放，图就会偏移/缩放/只露一部分。

判断方法：日志里 screenshot placed / screenshot surface 是否出现在 screenshot frame ready 之后；或给前端 onImage 和 finish_shot_place 打同一条时间线。

### 2.2 物理/逻辑坐标混用

- monitor 的 x/y/w/h 是物理像素；
- SetWindowPos / GetClientRect / WebView controller bounds 如果线程不是 per-monitor v2，可能按逻辑像素解释；
- 结果窗口位置/客户区与 monitor 物理矩形差一个 DPI 比例，冻结图整体平移。

判断方法：同屏打印 monitor、window outer、client、controller bounds、rasterization scale、image natural/client/rect、stage、devicePixelRatio。任何两个宽度比例不等，就是这条。

### 2.3 surface 缩放被设置两次

- finish_shot_place 里 apply_shot_rect 已经做过一次尺寸；
- sync_shot_surface 又 SetRasterizationScale + SetBoundsMode(RAW_PIXELS) + host child SetWindowPos + controller SetBounds；
- 如果调用顺序/次数不对，WebView 内容会按错误的 rasterization scale 渲染，出现缩在左上角/裁剪。

判断方法：只保留一次 finish_shot_place 调用，观察是否恢复；或在 sync_shot_surface 前后打印 controller Bounds / RasterizationScale。

### 2.4 BMP 行序/头

- LiveFrame 是 top-down BGRA；
- bmp_file 写正 height，并把行倒序写入；
- 已有单测 bmp_stores_rows_bottom_up；
- 如果仍怀疑，用一张已知棋盘格截图对照，排除上下翻转/stride 问题。

### 2.5 窗口位置锁 lock_shot_pos

- SetWindowSubclass 在 WM_WINDOWPOSCHANGING 里强制写回 SHOT_LOCK_X/Y/W/H；
- 如果 DPI 切换时系统先缩放窗口，锁又把它改回旧物理值，可能出现窗口/客户区不一致；
- 先临时去掉锁做 A/B，确认是不是它。

## 3. 诊断方案

### 3.1 临时坐标网格

在冻结图上叠一层 10% 网格 + 坐标标签（仅 debug），对比：

- 网格是否和桌面原有窗口边界对齐；
- 网格整体平移：窗口/坐标问题；
- 网格被缩放：surface/rasterization scale 问题；
- 网格只显示一部分：surface 尺寸/裁剪问题。

### 3.2 一次性日志

在 ensure_shown / finish_shot_place / sync_shot_surface / 前端 onImage 打同一组字段：

| 字段 | 来源 |
| --- | --- |
| monitor x/y/w/h | available_monitors |
| window outer x/y/w/h | outer_position / outer_size |
| client w/h | GetClientRect |
| controller bounds | ICoreWebView2Controller::Bounds |
| rasterization scale | ICoreWebView2Controller3::RasterizationScale |
| host child w/h | GetClientRect(host) |
| image natural w/h | img.naturalWidth/Height |
| image client rect | img.getBoundingClientRect() |
| stage client w/h | stage.clientWidth/Height |
| devicePixelRatio | window.devicePixelRatio |

### 3.3 判定表

| 观察 | 结论 | 先修 |
| --- | --- | --- |
| image rect = 0,0,stage；但内容偏 | surface/抓屏坐标 | P0/P1 |
| image rect 不是 0,0,stage | CSS/object-fit/inset | CSS |
| image natural 与 monitor 比例不等 | 帧尺寸/BMP | P4 |
| controller bounds ≠ client | surface 设置 | P0/P2 |
| raster scale 与 dpi/96 不等 | DPI | P1/P2 |
| window outer ≠ monitor rect | 位置/锁 | P1/P3/P5 |

## 4. 修复方案

### P0. 让 surface 设置同步、排在 emit 之前（先做）

目标：图开始加载前，窗口、host child、controller bounds、rasterization scale 已经稳定。

改法：

1. place_shot_physical 已经在主线程调用时，直接调用 finish_shot_place，不要再 run_on_main_thread 排队。
2. 如果存在非主线程调用，改成同步等待（channel + 超时），不要在图片加载后才完成。
3. ensure_shown 顺序改为：

```text
ensure_window
→ place_shot_physical（同步完成 surface）
→ present_shot
→ place_shot_physical（同步；如果 show 会改 DPI）
→ emit shot-refresh
```

4. finish_shot_place 里不要重复 apply_shot_rect；窗口尺寸只在 place_shot_physical 做一次，sync_shot_surface 只负责 host/controller。
5. 可选：前端 onImage 后回一个 shot_surface_ready，但这只是观测，不解决顺序；顺序要在 Rust 侧保证。

验收：日志里 screenshot placed / screenshot surface 一定早于 screenshot frame ready。

### P1. 统一物理坐标

- monitor 的 x/y/w/h 一律物理像素；
- 窗口位置/尺寸用物理像素；
- 主线程在 SetWindowPos / GetClientRect / sync_shot_surface 前后设 SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)（或确认进程已是 per-monitor v2）；
- 不要混用 LogicalSize / PhysicalSize；
- 前端 stage 用 100vw/100vh，image object-fit: fill；如果 CSS viewport 与物理/scale 不一致，优先修 surface，不要用 transform 补偿。

### P2. 只保留一条 DPI 路径

二选一，不要混：

路径 A（推荐先试）：让 WebView2 自己处理 DPI

- 去掉 SetRasterizationScale / BOUNDS_MODE_USE_RAW_PIXELS；
- 窗口用物理尺寸，host child/controller 按 client 物理尺寸；
- 让 WebView2 默认 rasterization 处理；
- 如果出现缩在左上角，再回到路径 B，不要同时开两套。

路径 B：全 raw pixels

- SetRasterizationScale(scale) 只设一次；
- SetBoundsMode(COREWEBVIEW2_BOUNDS_MODE_USE_RAW_PIXELS)；
- host child / controller bounds 全部物理像素；
- 不再用 Tauri set_size 二次改窗口；
- 每次 show 后只调用一次 finish_shot_place。

### P3. 去掉/放宽位置锁做 A/B

- 临时注释 SetWindowSubclass(lock_shot_pos)，看偏移是否消失；
- 如果锁导致 DPI 切换后的强制回写，改成只在用户手动移动时锁，或只在 WM_WINDOWPOSCHANGING 里纠正 1–2px 级偏差；
- 不要让锁和 SetWindowPos 互相打架。

### P4. BMP / 帧校验

- 保持 top-down LiveFrame；
- bmp_file 正 height + 行倒序；已有单测；
- 加一个 4×4 已知像素的 BMP 解码对照；
- 如果怀疑帧尺寸，先用 DAODIAN_SHOT_PNG=1 走 PNG 路径对照，确认偏移是否只在 raw/BMP 出现。

### P5. 兜底

如果 P0–P4 后仍偏移：

1. 退回标准 Tauri 窗口尺寸：set_position(PhysicalPosition) + set_size(PhysicalSize)，不自定义 surface；先保证图像正确，再优化首帧。
2. 原生覆盖层：freeze 图直接画在 Win32 窗口的 DIB 上，不经过 WebView2 的 DPI/surface；标注工具条单独小窗口。约 1–2 周。

---

## 5. 验收

1. 冻结图与桌面 1:1 对齐：10% 网格在 100%/125%/150%/200% 下都对齐。
2. 图像完整覆盖窗口，不出现只露一条/缩在左上角。
3. 图像不被拉伸：naturalWidth/Height、clientWidth/Height、stage 比例一致。
4. 多屏（含负坐标、竖屏、混合 DPI）位置正确。
5. 选区/标注坐标与冻结图一致；导出区域与选区一致。
6. screenshot surface 日志早于 frame ready；不再有 surface 后改。
7. 连续打开/关闭 10 次不出现偶发偏移。
8. PNG 路径（DAODIAN_SHOT_PNG=1）与 raw/BMP 路径像素一致。
9. 去掉位置锁后行为不回退；保留锁也能稳定。
10. 100% 复现的原偏移用例通过。

---

## 6. 这一轮不做什么

- 不改抓屏区域算法（capture_bgra 的 monitor DC / 0,0 先保留）。
- 不同时重写 freeze 和 live 两套；先修 freeze。
- 不先用原生覆盖层掩盖问题；先用 P0/P1 定位 surface/DPI。
- 不用 CSS transform 去补偿偏移；那会把导出/选区坐标一起带偏。
- 不为偏移牺牲首帧；先保证对齐，再优化延迟。

## 7. 第二轮：P0 同步后仍偏，改查坐标源

P0（surface 同步）做完仍偏，说明不只是「图先到、surface 后改」。现在按「采集坐标源」和「显示坐标源」二分，不要再继续加 DPI 补丁。

### 7.1 先分清是采集偏还是显示偏

按顺序做三个 A/B：

1. **PNG 路径对照**：设 DAODIAN_SHOT_PNG=1，走 PNG 落盘；如果 PNG 也偏，问题在窗口/显示；如果只有 raw/BMP 偏，问题在帧/BMP。
2. **导出原始帧**：把 LiveFrame/BMP 直接写到磁盘，用系统看图打开；如果原图就偏，采集区域错了；如果原图正确，显示错了。
3. **坐标网格**：冻结图上叠 10% 网格 + 坐标标签，和桌面原有窗口边界对比；整体平移=窗口/坐标，缩放=surface/scale，裁剪=surface 尺寸。

### 7.2 现在最可疑：monitor 坐标源不一致

从现象看，冻结图像是「从桌面偏右的位置开始截」，导致左边文字被切掉。最可疑的是：

- 窗口/捕获使用的 monitor x/y/w/h 来自 Tauri available_monitors；
- capture_bgra 用 monitor_dc 按 x/y/w/h 精确匹配；匹配失败就退回 GetDC(NULL) + BitBlt(x,y)；
- 如果 Tauri 返回的是逻辑坐标、Win32 枚举是物理坐标，monitor_dc 匹配失败，fallback 的 x/y 就是错的；
- 结果：抓到的区域整体偏移，图里的内容左移/右移，左边被切掉。

**判断方法**：在 capture_bgra 里打印：

```text
requested rect x,y,w,h
monitor_dc found / fallback
matched device / monitor rect
thread dpi context
```

如果出现 fallback，或者 matched rect 与 requested 不一致，就是这条。

### 7.3 修复：只保留一个 Win32 物理坐标源

1. 用 EnumDisplayMonitors + GetMonitorInfoW(MONITORINFOEXW) 枚举显示器，拿 rcMonitor（物理）和 szDevice；
2. 用 GetDpiForMonitor(MDT_EFFECTIVE_DPI) 拿 scale；
3. **捕获和窗口放置都用这一份 rect/device/scale**，不要再混 Tauri 的 monitor 几何；
4. 捕获用 CreateDCW(szDevice) + BitBlt(0,0,w,h)，不要静默 fallback；fallback 必须记日志并改为物理虚拟桌面坐标；
5. 窗口用 SetWindowPos 放到同一 rcMonitor，主线程设 per-monitor v2；
6. 索引映射：按 monitor 顺序或 device 名固定 shot-N，不要在两个枚举之间靠 x/y 猜。

### 7.4 修复：窗口/表面只走一条路径

- 先选路径 A：不设 SetRasterizationScale/BoundsMode，窗口按物理 rcMonitor，WebView2 默认 DPI；测试。
- 如果 A 出现缩左上，再选路径 B：全 raw pixels，SetRasterizationScale 只设一次，host/controller bounds 全部物理像素，不再用 Tauri set_size 二次改。
- 不要 A+B 混用。
- 临时去掉 lock_shot_pos 做 A/B；位置锁只应在用户手动移动时生效，不能在 DPI 切换时强制回写。

### 7.5 如果仍偏

- 退回标准 Tauri 窗口：set_position(PhysicalPosition) + set_size(PhysicalSize)，不碰 WebView2 surface，先保证图像正确；
- 或原生覆盖层：DIB 直接画冻结图，不经过 WebView2 DPI；
- 不要用 CSS transform 补偿偏移：选区、导出、贴图会一起偏。

### 7.6 第二轮验收

1. capture_bgra 日志里不再出现 monitor_dc fallback；matched rect = requested rect。
2. PNG 路径与 raw/BMP 路径在 100%/125%/150% 下都不偏。
3. 冻结图与桌面网格 1:1；左边文字不再被切。
4. 窗口 outer/client/controller bounds 三者一致。
5. 多屏、负坐标、竖屏、混合 DPI 都能对齐。
6. 去掉位置锁也能稳定；保留锁也不偏。
7. 连续 10 次打开不出现偶发偏移。

---

## 8. 一句话

偏移大概率不是抓屏抓错了，而是图已经加载、surface 才异步改尺寸/缩放。先让 finish_shot_place 同步、排在 emit 之前，再统一物理坐标和 DPI 路径；surface 稳定后，冻结图就会对齐。
