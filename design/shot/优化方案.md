# 到点 · 截图性能优化方案

> 状态：**优化方案**（2026-11）· 不改产品交互，只改链路的耗时和卡顿。
> 快捷键响应单独成文：[快捷键响应优化方案.md](快捷键响应优化方案.md)；冻结与另存分别见 [冻结优化方案.md](冻结优化方案.md)、[另存优化方案.md](另存优化方案.md)。
> 对象：当前「热键 → shot 线程 → 每屏抓屏线程 → 主线程 show → shot-N WebView → convertFileSrc」链路。
> 目标：热键到第一张冻结图不超过 250–450ms（按分辨率），拖选 / 画笔稳定 60fps，多屏同时出现，内存峰值可控。
> 结论先行：**先砍重复工作，再换传输和采集**。O0 不动抓屏架构：前端去双绘、主线程批量 show、加图片就绪握手、轻量 shot 入口；O1 再把 PNG 落盘往返换成原始帧、把复制/保存的 base64 去掉；WGC / 单窗口跨屏放最后。

---

## 0. 一页结论

| 序 | 优化 | 动作 | 预期 | 工期 | 风险 |
| --- | --- | --- | --- | --- | --- |
| O0-1 | 前端绘制 | 去双绘、rAF 合并、CSS 暗层、canvas 只画选区、画笔 push | 拖选/画笔从掉帧到 60fps | 1–1.5 天 | 标注坐标/裁剪回归 |

## 1. 现状：卡在哪

### 1.1 一条链路的真实顺序

```text
t0 热键
  │
  ├─ shot 线程：available_monitors
  ├─ 每屏抓屏线程（并行）：
  │    BitBlt → GetDIBits → BGR 交换 → PNG 编码 → 写盘
  ├─ join 所有抓屏线程（等最慢的一屏）
  ├─ 逐屏 on_main（串行）：
  │    ensure_window → set_position/size → show → reveal → emit
  └─ WebView：
       invoke shot_screen → convertFileSrc → 读 PNG → 解码 → onImage → 首次 paint
```

关键不是某一段特别慢，而是**每一段都要等前一段全部完成**。多屏时，`join`、N 次主线程往返、N 次 PNG 解码会叠加。

### 1.2 按现象拆

| 现象 | 直接原因 | 代码位置 |
| --- | --- | --- |
| 按下后要等一会才黑/才出图 | 等所有屏抓完 + 逐屏 show + 图未解码 | `capture_screens` / `show_one` / `ensure_shown` |
| 多屏一块一块出现 | 每屏一次 `on_main`，还重复 `reveal_shot_windows` | `show_one` / `ensure_shown` |
| 出现暗底再突然变亮 | `show` 早于图片 `onImage`；stage 背景 + canvas 各一层暗 | `.shot-stage` / `paint` |
| 拖选掉帧 | 每个 pointermove 触发两次全屏 canvas 重绘 | `watch(... paint)` + `onMove` 里的 `paint` |
| 画笔越画越卡 | 每个点复制整个 points 数组，O(n²) | `points: [...current.points, point]` |
| 整机卡一下、风扇转 | N 个抓屏线程各分配整屏 RGBA + PNG；N 个完整 Vue WebView 预热 | `capture_rect` / `write_png` / `do_prewarm` |
| 复制/保存卡 0.5–1s | `toDataURL` 同步编码 + base64 IPC + Rust 再解码 | `renderPng` / `shot_copy` / `shot_save` |
| 键盘快捷键要先点一下 | `focused(false)` + `SW_SHOWNOACTIVATE`，没有真正的 `set_focus` | `ensure_window` / `shot_focus` |

### 1.3 当前日志测不到用户看到图的时间

`screenshot session opened in Xms` 是在 `show` 之后打的，**不包含**：

- `emit` 到前端的耗时；
- asset 读 PNG；
- WebView 解码；
- 首次 `paint`。

所以会出现「日志看着 200ms，体感 800ms」。优化前先补时间点，见 §5。

## 3. O0：先做，4–6 天

### 3.1 前端绘制：从「两次全屏」到「一帧一次」

**现状**：`watch([selection, shapes, drag, phase, ready], () => paint())` 已经在变化时画一次；`onMove` 里又直接 `paint()`。一次 pointermove 至少两次全屏 `fillRect` + `clearRect`；4K 的 canvas 约 8.3MP，3440×1440 约 5MP。

**改法**：

1. 删除所有直接 `paint()`，统一走调度：
   ```ts
   let raf = 0;
   function schedulePaint() {
     if (raf) return;
     raf = requestAnimationFrame(() => {
       raf = 0;
       paint();
     });
   }
   watch([selection, shapes, drag, phase, ready], schedulePaint);
   ```
2. 暗层从 canvas 拿出来：选区块用一个绝对定位的 `div`，用 `box-shadow: 0 0 0 9999px rgba(4,7,11,.5)` 压暗外部；canvas 不再 `fillRect` 全屏。
3. canvas 只覆盖选区（或只清脏区）：尺寸 = 选区尺寸，位置 = 选区位置，`drawShapes` 用局部坐标；标注本来就裁在选区内，正好。
4. 画笔不要复制数组：`current.points.push(point)`，然后 `schedulePaint()`；如果需要响应式，给 `drag` 加一个 `version` ref，或直接 `triggerRef(drag)`。
5. 缓存布局：`stage.clientWidth/clientHeight`、`getBoundingClientRect` 在 pointerdown 时取一次，窗口大小变化时再更新；不要在每次 move 里读。
6. 拖拽时 `sizeLabel` / `barStyle` 的 DOM 更新保持，但不要触发额外 canvas 绘制。

**预期**：去掉一次全屏 fill + 一次全屏 clear，去一次重复 paint；4K 拖选从 20–40ms/帧降到 5–10ms，60fps 稳定。

**文件**：`src/features/shot/ShotOverlay.vue`、`src/features/shot/annotate.ts`。

**风险**：选区坐标、裁剪、文字/箭头在局部 canvas 的坐标变换；用现有选区测试集 + 4K/125% 手工验收。

### 3.2 首帧：批量 show + 图片就绪握手

**现状**：每屏一次 `on_main`（`show_one`），每次 `show → reveal → emit`；`show` 完成就认为打开了，图片还在解码。

**改法**：

1. **批量主线程操作**：把 N 屏的 `ensure_window` / `set_position` / `set_size` / `show` 收进**一个** `run_on_main_thread` 闭包，减少 N 次同步往返。
2. **一次 emit**：用 `emit_to("shot-N", "shot-refresh", index)`，不要 `app.emit` 广播；每屏只收自己的事件。
3. **去掉重复 reveal**：`reveal_shot_windows` 只在批量 show 时调一次，不在每屏调。
4. **加就绪握手**：
   - 前端 `onImage` 成功后 `invoke("shot_ready", { index })`；
   - Rust 记录每屏 ready；全部 ready 后把窗口显示出来（或先把窗口以 opacity 0 / 离屏方式显示，ready 后变可见）；
   - 如果隐藏 WebView 不解码图，退回「先 show 但 stage 透明」，至少不要暗底闪。
5. **去掉双重暗层**：stage 背景在 ready 前保持透明或只保留一层；`is-ready` 后再上暗层。加载中给一个小胶囊「正在冻结…」，不要给近黑屏。
6. **焦点**：批量 show 后对 active screen 调 `window.set_focus()`（或至少 `set_focus` 一次），否则键盘快捷键要用户先点一下。

**预期**：所有屏同时出现；不再有「暗底 → 变亮」；N 次主线程往返降为 1 次；用户看到的第一帧就是冻结图。

**文件**：`src-tauri/src/shot.rs`、`src/features/shot/ShotOverlay.vue`。

**风险**：隐藏 WebView 可能被节流，图片不加载；先做 A/B：隐藏加载 vs opacity 0 vs 直接 show + 透明 stage。选实测最快的。

### 3.3 入口与预热：别让 shot 窗口加载整个应用

**现状**：`index.html?window=shot` 仍然执行 `main.ts`，加载 `App.vue` 的全部 import 和全部 CSS；当前构建约 **978KB JS + 82KB CSS**。`do_prewarm` 在启动时创建每屏一个这样的 WebView，且和 `Open` 共用同一个 worker 队列。

**改法**：

1. **独立轻量入口**：
   - 新增 `shot.html`（根目录）和 `src/shot.ts`；
   - `shot.ts` 只 `import ShotOverlay` + 少量 reset CSS，不 import `App.vue` / AppShell / Tiptap / notes / pet；
   - Vite `build.rollupOptions.input` 增加 `shot.html`；
   - Rust 的 URL 从 `index.html?window=shot&screen=N` 改为 `shot.html?screen=N`；
   - 预热和按需创建都走这个入口。
2. **预热可取消、低优先级**：
   - 截图关闭时不预热；
   - 预热放独立线程/队列，不要和 `Open` 共用 `WORKER`；
   - 启动后延迟 1–3 秒、一屏一屏创建；
   - `trigger` 时设置取消标记，预热在下一屏前退出。
3. **WebView2 参数**：加 `--disable-background-timer-throttling`、`--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding`，实测隐藏窗口的 `show → 首帧` 时间；不要假设「窗口创建了」就等于「首帧就绪」。
4. **预热的验收**：记录每屏 `build` 和 `show → onImage` 的时间；如果预热没有改善首帧，就只保留按需创建，别再启动时创建 N 个。

**预期**：shot 窗口 JS/CSS 解析从 ~1MB/82KB 降到几十 KB/十几 KB；启动主线程不被 N 个 WebView 抢；首帧更快，内存更低。

**文件**：`shot.html`、`src/shot.ts`、`vite.config.ts`、`src-tauri/src/shot.rs`。

**风险**：样式 token 拆分、开发/生产入口差异；先保证主窗口不受影响。

### 3.4 复制/保存：异步 + 二进制，去 base64

**现状**：`renderPng` 用 `new Image().decode()` 再解码原图，`canvas.toDataURL` 同步编码，base64 通过 `invoke` 传给 Rust，Rust 再 `decode_png`。4K 大选区会卡主线程 0.5–1s。

**改法**：

1. 用 `canvas.toBlob("image/png")` 异步拿 bytes；
2. 不要再 `new Image().decode()`：加载时用 `createImageBitmap(imageRef)` 缓存一份，导出直接 `drawImage`；
3. 传输：
   - 优先：`tauri::ipc` 原始字节 / 自定义协议 / `Channel`，避免 base64；
   - 兜底：用 `plugin-fs` 把 bytes 写到临时 `.png`，再把路径交给 Rust（至少去掉 base64 和同步 `toDataURL`）；
4. Rust 新命令 `shot_copy_bytes` / `shot_save_bytes`：直接复制/写 bytes，不再 `decode_png` + 重新编码；
5. 贴图同理，避免 `shot_pin(png: String)` 的 base64。

**预期**：4K 复制从 0.5–1s 降到 200ms 内；保存不再二次编解码。

**文件**：`ShotOverlay.vue`、`shot.rs`、`Cargo.toml` / capabilities（如果新增命令/插件）。

**风险**：Tauri 二进制 IPC 的具体形态要先用小 demo 验证；不支持就退回临时文件。

## 4. O1：传输与采集，4–6 天

### 4.1 去掉「PNG 落盘 → asset 读回 → 解码」

**现状**：抓屏线程 `write_png`（Fast + NoFilter + RGBA）落盘，WebView 再 `convertFileSrc` 读回、解码。4K RGBA 原始 33MB，PNG 仍可能 5–20MB；多屏叠加明显。

**方案 A（推荐先试）：原始帧 + 自定义协议**

- 抓屏线程产出 RGBA/BGRA + 宽高 + stride，存进 session 的内存帧表；
- 注册 `shot://frame/{index}`（或 `tauri::ipc::Response` 原始字节），前端 `fetch` → `arrayBuffer` → `createImageBitmap(new ImageData(...))`；
- 帧在「全部 ready」后释放；刷新/重截时重新抓；
- 3×4K 峰值约 100MB 原始帧，比 PNG 解码峰值可控；如果内存吃紧，先只保留当前屏，其他屏按需。

**方案 B（保守）：BMP / 无损 WebP**

- BMP 头 + BGRA，浏览器解码比 PNG 快，文件更大；适合先验证「解码是不是瓶颈」；
- 或 `image` 编 WebP 无损，体积小但编码 CPU 高；截图文字不适合有损 JPEG。

**方案 C（最小改动）：继续 PNG，但改参数**

- RGB8（截图 alpha 永远 255），去掉 alpha；
- `FilterType::Adaptive` / `Sub`，不要 `NoFilter`；文件更小；
- 先 benchmark 编码时间 vs 解码/传输时间，不要凭感觉。

**预期**：去掉 PNG 编码、写盘、读盘、解码四段，每屏省 100–300ms；4K 首帧明显提前。

**风险**：原始帧传输的 IPC/内存带宽；需要 feature flag + fallback 到 PNG。

### 4.2 抓屏：少一次全量拷贝

**现状**：`capture_rect` 先 `CreateCompatibleBitmap`，再 `GetDIBits` 拷进 `Vec`，再 BGR→RGB 全量交换；4K 每屏两次 33MB 级搬运。

**改法**：

- `CreateDIBSection`（top-down 32bpp）+ `BitBlt` 直接写 DIB bits，省掉 `GetDIBits` 的第二次拷贝；
- BGR→RGBA 的交换放到编码/传输线程，或分块并行；
- 复用每屏的 DIB / 缓冲，避免每次分配零初始化 33MB；
- 多屏同时抓时限制并发（如 2 个），或给抓屏线程 `THREAD_PRIORITY_BELOW_NORMAL`，先保 UI；
- 后续再评估 WGC / DXGI（O2）。

**预期**：抓屏 CPU 降 30–50%，峰值内存降；系统级卡顿减少。

**风险**：GDI 资源生命周期、DIB 方向、DPI；需要逐屏对比像素。

### 4.3 事件与焦点

- `emit_to` 替代广播；
- 批量 show 只 `reveal` 一次；
- active screen 真正 `set_focus`；
- 多屏时只允许一个活动屏，其他屏不响应键盘；
- 这些是低风险收尾，放在 O1。

## 5. 先测量，再优化

当前日志只有 `screenshot session opened in Xms`，不够。加以下时间点（debug 构建或临时日志）：

| 标记 | 位置 | 含义 |
| --- | --- | --- |
| t0 | 热键触发 | 用户按下 |
| t1 | capture_screens 返回 | 所有屏抓完/写完 |
| t2 | 批量 show 完成 | 窗口可见 |
| t3 | 每屏 emit 发出 | 前端开始加载 |
| t4 | 每屏 onImage | 图解码完成 |
| t5 | 每屏首次 paint | 可交互 |

前端再加：

- `performance.mark("shot-move-start")` / `shot-paint-end`，统计 pointermove → paint 的帧时间；
- 画笔 5 秒的帧数、掉帧数；
- 复制/保存的 `toBlob` / IPC / 剪贴板耗时。

验收环境至少覆盖：

- 1 屏 1080p / 1 屏 3440×1440 / 1 屏 4K / 2–3 屏 4K；
- 100% / 125% / 150% DPI；
- 冷启动第一次截图 vs 预热后截图；
- 空选区 / 大选区 / 画笔长线 / 复制 / 保存。

## 7. 风险与回滚

| 风险 | 对策 |
| --- | --- |
| 隐藏 WebView 不解码图，ready 握手卡住 | 500ms 超时后强制 show；或改 opacity 0 + 可见窗口；保留旧路径 feature flag |
| 原始帧内存/带宽反而更慢 | 先做 PNG-vs-BMP-vs-raw 的 A/B；raw 失败回退 PNG |
| 轻量入口样式不一致 | 只抽 ShotOverlay 需要的 reset/token；截图页与主窗口分别验收 |
| DIB 抓屏边界/方向错误 | 逐屏像素对比；保留旧 capture 路径开关 |
| 二进制 IPC 不支持 | 退回 `plugin-fs` 临时文件 + 路径；至少去掉 base64 |
| 多屏 DPI 偏移 | 原有物理像素测试矩阵；O0/O1 不改坐标语义 |

所有优化用 feature flag 或环境变量包一层；出问题能回到现在的链路。

## 8. 验收

1. 1080p 热键 → 所有屏可见 ≤ 150ms；4K 单屏 ≤ 300ms；3×4K ≤ 450ms。
2. 热键 → 每屏冻结图 onImage ≤ 250 / 450 / 700ms（按上表）。
3. 多屏出现错峰 ≤ 50ms；不再一块一块出现。
4. 首帧不再是近黑暗底；不再「暗底突然变亮」。
5. 拖选 60fps；4K 每帧 paint ≤ 12ms；无肉眼掉帧。
6. 画笔连续 5 秒：帧率稳定，不随点数增长而变慢。
7. 4K 复制 ≤ 200ms；保存 ≤ 800ms；主线程无 0.5s 以上长任务。
8. 3×4K 会话峰值内存增量 ≤ 150MB；结束后回到基线。
9. 启动预热不再阻塞主线程超过 50ms；截图关闭时不创建 shot 窗口。
10. Esc / 右键分层、贴图原位、保存取消、多屏负坐标、125% / 150% DPI 全部回归通过。
11. 冷启动第一次截图与预热后截图都测；不能只测热态。
12. 关闭 feature flag 能回到现有链路，行为一致。

---

## 9. 不做（这一轮）

- 不先上 WGC / DXGI：采集升级是 O2，先确认瓶颈不在前端和 PNG 往返。
- 不做单窗口覆盖虚拟桌面：跨屏收益大，但 DPI 风险高，等 O1 稳定后再评估。
- 不做 GPU shader 合成 / 自绘窗口：收益不确定，维护成本高。
- 不为了「看起来快」省略冻结：先保证截图内容一致，再谈延迟。
- 不把截图历史/云同步塞进这次优化：性能问题优先，功能扩展另排。

---

## 10. 一句话

**先让前端一帧只画一次、让窗口等图再显示、让 shot 窗口只加载截图页；再把 PNG 落盘往返换成原始帧，把复制/保存的 base64 换成二进制。采集库最后再换。**
